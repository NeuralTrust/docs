# Use Cases

The **Use Cases** view in Telemetry holds the rule catalog that drives [Alerts](/platform/alerts). Each **use case** is a detection rule evaluated on a schedule by the AlertEngine over metadata events in the NeuralTrust telemetry store.

- **Predefined** use cases (`nt-uc-NNN`) ship with the platform. They are read-only: enable or disable them per team from the row action menu. To change one, open it and choose **Copy to custom** — see [Copy a predefined use case](#copy-a-predefined-use-case).
- **Custom** use cases are team-owned. Create them in the rule builder; **Edit** and **Delete** are offered in the detail panel for custom use cases only.

Every use case, predefined or custom, also has a **Notifications** section in its detail panel: who new alerts are assigned to, and whether that person is emailed. It is saved per team.

Open **Telemetry → Use Cases → Create use case** (or edit a custom use case) to use the rule builder described below.

---

## Rule builder tabs

The create/edit side panel has three tabs. Every change compiles live into the **Rule preview** tab.

<Steps>
  <Step title="General">
    The rule **Name** (required — the YAML `title`) and **Description** (free text, shown as the logic in the use case detail). Under **Alert Output**: the **Severity** of the alerts the rule raises, an optional **Default assignee**, and whether to **email the assignee when an alert fires** (only with an assignee).
  </Step>
  <Step title="Conditions">
    The **Products** the rule covers and the **scope** within each one, then **Attributes or windowed measures**: the condition rows, joined with **And** / **Or**. Below them, **Number of times the condition must occur** and, when that number is above 1, the **Time window**. With both products selected, this tab becomes the [cross builder](#cross-rules).
  </Step>
  <Step title="Rule preview">
    Read-only YAML — exactly what AlertEngine stores and evaluates. Use it to check the compiled rule before saving.
  </Step>
</Steps>

AlertEngine validates the rule when you save it. It rejects a field that does not exist for the rule's product, an operator the field does not support, and an enum value outside the field's list. The builder flags the same problems on the condition row before you save.

## Products and scope

The **Products** selection drives both the compiled `source` and the field picker, which shows **only fields valid for that product**. It lists the products your organization has.

- **TrustGate** only → `source: trustgate`.
- **TrustGuard** only → `source: trustguard`.
- **Both** → `source: cross`. See [Cross rules](#cross-rules).

### Scope

Scope is a two-level cascade per product. Pick the parent, then its children; an empty level means "no filter".

| Product | Parent | Child | Compiles to |
|---|---|---|---|
| TrustGate | **Gateways** | **Applications** (loaded from the selected gateways) | `gateway_id` and `consumer` predicates |
| TrustGuard | **Instances** | **Collectors** (loaded from the selected instances) | `collector_id` predicate only |

Scope predicates are ANDed into every OR group, so they constrain the whole rule. TrustGuard **instances** only narrow which collectors are offered; the instance selection itself is not saved. To filter on an instance, add a condition on **TrustGuard instance ID** (`guard_id`).

## Conditions

### AND / OR logic

Each condition row is a predicate: **field · operator · value**.

- **And** between rows keeps predicates in the same group (all must match).
- **Or** starts a new group. The compiler emits YAML `any:` — disjunctive normal form (OR of AND-groups).

Click the **And** / **Or** pill between rows to toggle the connector. Use **And +** or **Or +** under a row to insert a new condition with that connector.

### Operators

| Operator | YAML | Meaning |
|---|---|---|
| **is** | `eq` | Equals |
| **in** | `in` | One of a comma-separated list |
| **contains** | `contains` | Substring match |
| **starts with** | `prefix` | Text begins with the value |
| **ends with** | `suffix` | Text ends with the value |
| `>`, `≥`, `<`, `≤` | `gt`, `gte`, `lt`, `lte` | Numeric comparison |

Which operators a field offers depends on its type:

| Value type | Operators |
|---|---|
| Text | **is**, **in**, **contains**, **starts with**, **ends with** |
| Identifier (an ID, session, trace, HTTP method) | **is**, **in** |
| Security tags | **contains** only |
| Number | **is**, **in**, `>`, `≥`, `<`, `≤` |
| Detection confidence | `≥`, `>`, `≤`, `<`, **is** |
| Boolean | **is** (**True** / **False**) |
| Enum | **is**, **in** — only the values the picker lists, case-sensitive |

### Field picker

Fields are grouped in the dropdown, and each option carries a short description. The groups, in order, are **Outcome & status**, **Request**, **Identity**, **Latency & usage**, **Tools** (MCP), **Detection** (TrustGuard), and **Coverage**. The field list is served by AlertEngine, so the picker always shows exactly the fields a rule can use.

The tables below give each field's picker label and its DSL key, the key written into the rule. See [Event schema](/platform/event-schema) for how each key maps to stored events.

### Fields for both products (11)

| Status outcome | `status.outcome` | enum · `is` `in` | Final outcome recorded on the event. TrustGuard: `block`, `transform`, `report`, `allow`, `skip` (a Skip gate matched; no detector ran), `ask`, or `error` (the request returned 4xx/5xx). TrustGate: the result of the last provider attempt, `success`, `retryable`, or `terminal`; not set on MCP events or when no provider was called. A rule accepts only the values of its own product. |

All 11 fields for both products, plus:

| Field | DSL key | Type · operators | Description |
|---|---|---|---|
| Direction | `direction` | enum · `is` `in` | Whether the event is an `input` (prompt) or `output` (response) evaluation |
| Protocol | `protocol` | enum · `is` `in` | Request protocol: `llm`, `mcp`, `a2a` |
| Collector ID | `collector_id` | identifier · `is` `in` | TrustGuard collector that evaluated the request |
| Collector name | `collector_name` | text · all text operators | Display name of the collector |
| TrustGuard instance ID | `guard_id` | identifier · `is` `in` | TrustGuard instance (one per environment) the collector belongs to |
| Policy ID | `policy_id` | identifier · `is` `in` | Runtime policy that evaluated the request |
| Policy name | `policy_name` | text · all text operators | Display name of the runtime policy |
| Detector latency (ms) | `latency.detectors_ms` | number · all number operators | Time spent running detectors |
| Overhead latency (ms) | `latency.overhead_ms` | number · all number operators | Processing overhead outside detectors |
| Detection type | `detection.type` | enum · `is` `in` | Normalized detection category: `prompt_injection`, `secrets`, `pii`, `toxicity`, `behavioral_threat`, `multi_turn_escalation`, `code_injection` |
| Detection action | `detection.action` | enum · `is` `in` | Action the detector took: `block`, `transform`, `report` |
| Detection confidence | `detection.confidence` | number · `≥` `>` `≤` `<` `is` | Detector confidence score between 0 and 1 |
| Detection enforced | `detection.enforced` | boolean · `is` | True when the action is `block` or `transform` |
| Detector not evaluated | `coverage.not_evaluated` | boolean · `is` | True when at least one detector failed to run (for example a timeout or a crash), so the request passed without that detector's check |
| Failed detectors | `coverage.failed_detectors` | number · all number operators | How many detectors failed to run on the request |

The **detection** fields compile into a separate `detection:` block in the rule YAML, matched against each finding in the detector chain; a detection row only matches a detector that found something. All other fields, the **coverage** ones included, compile into `match:`.

<Warning>
**There is no `jailbreak` detection type.** The engine normalizes jailbreak signals — and anything raised by the `prompt_guard` / `tool_guard` plugins — into `detection.type = prompt_injection`. To match jailbreaks specifically rather than all injection attempts, filter on the `security` tag with `contains` instead.
</Warning>

<Warning>
**IP address is not a rule field.** The client IP is stored with each event for investigation, but a rule can neither match nor group on it. Group by **Session** or **Application** instead for surge and anomaly rules.
</Warning>

## How many times, and over what window

**Number of times the condition must occur** sets when the rule raises an alert. It defaults to **1**.

| Value | Behaviour | Compiles to |
|---|---|---|
| **1** | Every matching event raises an alert. No time window. | `kind: per_event` |
| **2 or more** | An alert is raised when the condition occurs that many times within the time window. | `kind: windowed`, with `window`, `threshold`, and `group_by` |

Above 1, the **Time window** section appears:

| Control | Description |
|---|---|
| **Within** amount + unit | Window length, in minutes or hours |
| **per** | The key occurrences are counted separately for: **Application** (default), **Session**, **App** (the gateway or collector), or **Route** (TrustGate only) |

The number you enter is stored as `threshold`. **Application** is the engine's default grouping (`entity`), so it is omitted from the compiled YAML; the other keys compile to `group_by: session`, `group_by: app`, or `group_by: route`.

```yaml
kind: windowed
window: 10m
group_by: session
threshold: 5
```

A rule that counts **distinct values** instead of events (`kind: aggregate` with a `count_distinct` metric) is kept when you copy or edit one, but the builder has no control to create it.

## Cross rules

Selecting **both** products turns the Conditions tab into the cross builder, which compiles to `source: cross` and `kind: cross`:

| Control | Description |
|---|---|
| **TrustGate conditions** | Predicates on gateway traffic. `match` only — the engine rejects detection predicates on the gate side |
| **TrustGuard conditions** | Predicates on guard events, including `detection.*` |
| **Correlate on** | Shared key joining a gateway event to a guard event: **Application** (`entity`, default) or **Session** |
| **Time window** | Required for cross rules |
| **Threshold** | Optional: minimum correlated events within the window before alerting |

Each side needs at least one predicate — a condition row or a scope selection. The conditions on each side are combined with AND; a cross rule has no OR groups. They compile under `gate:` and `guard:`, and **Session** compiles to `correlate_on: session`.

## Copy a predefined use case

A predefined use case cannot be edited, so to change one, open it and choose **Copy to custom**. The builder opens with the rule's logic and the name `<name> (copy)`; change what you need and save. If the original is on, tick the option to **turn it off when the copy is saved**, so only your copy raises alerts.

The copy is offered only when the builder can express the rule exactly, so that saving it unchanged saves the same rule. It is not offered for a rule that:

- reads the console audit log, which custom use cases cannot use;
- measures a ratio or a percentile;
- raises one alert per window (a windowed rule with a threshold of 1), because the builder makes a threshold of 1 a per-event rule;
- uses anything else the builder cannot express.

## Example compiled rules

### Per-event TrustGuard detection (similar to nt-uc-101)

```yaml
title: "High-Confidence Threat"
description: "Blocked threat with confidence >= 0.90"
source: trustguard
severity: high
kind: per_event
detection:
  - field: detection.confidence
    gte: 0.90
  - field: detection.action
    eq: "block"
```

### Windowed TrustGate auth anomaly (similar to nt-uc-201)

```yaml
title: "Auth Anomaly"
source: trustgate
severity: high
kind: windowed
window: 5m
group_by: session
threshold: 10
match:
  - field: status.code
    in: [401, 403]
```

### OR groups (401 or 403 per event)

```yaml
title: "Unauthorized or forbidden"
source: trustgate
severity: medium
kind: per_event
any:
  - match:
      - field: status.code
        eq: 401
  - match:
      - field: status.code
        eq: 403
```

### Guardrail failed open (similar to nt-uc-401)

```yaml
title: "Guardrail failed open"
source: trustgate
severity: high
kind: per_event
match:
  - field: policy.failed_open
    eq: true
```

## Rule kinds (evaluation models)

| `kind` | Fires when | YAML extras | Created by the builder |
|---|---|---|---|
| `per_event` | Any single matching event | — | Yes: the condition must occur once |
| `windowed` | Event count ≥ `threshold` per `group_by` within `window` | `window`, `group_by`, `threshold` | Yes: the condition must occur 2 or more times |
| `aggregate` | A metric — `ratio`, `p95`, `p90`, `avg`, `sum`, or `count_distinct` — crosses its threshold | `window`, `group_by`, `metric:` block | No. `count_distinct` rules are kept when copied or edited; the other metrics are used by predefined use cases |
| `cross` | TrustGate ⋈ TrustGuard on `correlate_on` | `window`, `gate:`, `guard:` | Yes: both products selected |
