---
title: "Files"
description: "Upload, list, fetch, download and delete files through the gateway. The provider owns the file; the gateway owns nothing but the route."
---

Files use the OpenAI shape on the application URL and key: multipart upload to
`/v1/files`, then list, retrieve, `/content` download and delete by id.

```bash
curl -X POST "https://<llm-host>/<application-slug>/v1/files" \
  -H "X-AG-API-Key: <application key>" \
  -F purpose=assistants -F file=@notes.txt
```

## What the gateway does not own

File identity and retention belong to the provider. The gateway returns the
upstream file id as-is, keeps the upstream content type on download, and never
rewrites the multipart body. A file uploaded through one registry is not visible
through another, because it never existed anywhere but at that provider.

## Which registries can serve it

**OpenAI**, **Azure OpenAI**, **OpenRouter**, **xAI**, **Mistral** and
**Anthropic** expose a files store. OpenAI-compatible endpoints, Groq, Gemini,
Vertex, Bedrock and Cohere do not.

Anthropic is the one that answers in its own shape — `type`, `mime_type`,
`size_bytes` rather than OpenAI's `object` and `purpose` — and the gateway does not
translate that. Claude files are not available through Bedrock or Vertex.

## How it routes

Narrow to files-capable registries, then [routing](/trustgate/llm/routing). A JSON
`model` field, including `@provider/model`, is honoured only to pin a registry;
the upload itself has no model. Pinning an incapable registry is a `400`, an empty
pool a `503`.
