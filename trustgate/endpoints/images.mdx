---
title: "Images"
description: "Generate, edit, and vary images through OpenAI-shaped endpoints on the consumer LLM URL."
---

TrustGate exposes the fixed OpenAI image paths under a consumer slug and forwards them to
an image-capable registry.

## Endpoints

| Method | Path after consumer slug | Request body |
|---|---|---|
| `POST` | `/v1/images/generations` | JSON |
| `POST` | `/v1/images/edits` | JSON or `multipart/form-data` |
| `POST` | `/v1/images/variations` | JSON or `multipart/form-data` |

The `/v1/images` collection path by itself is not an endpoint. Only `POST` is accepted.

## Generate an image

```bash
curl -X POST "https://<llm-host>/<consumer-slug>/v1/images/generations" \
  -H "X-AG-API-Key: <consumer-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-image-1",
    "prompt": "A secure AI gateway represented as a minimalist blueprint"
  }'
```

For edits and variations, send the provider-compatible multipart form, including the
`model` field and image file. TrustGate preserves multipart payloads when forwarding them.

## Supported registries

Image routes can use:

- OpenAI
- Azure OpenAI
- OpenAI-compatible providers with image support
- OpenRouter

TrustGate filters out registries that do not support images. An explicitly selected
incompatible registry fails immediately; an empty compatible pool returns
`503 no_backend_available`.

## Behavior and limitations

- Consumer model allowlists are enforced for JSON and multipart requests.
- The provider's JSON response is returned without gateway-side image conversion.
- Image streaming is not supported.
- Availability of edits and variations depends on the selected provider and model.
- Unknown paths and extra path segments return **404**; unsupported methods return
  `400 invalid_request`.

Copy the host and credentials from the consumer **Connect** tab. See
[Auth](/trustgate/concepts/auth).
