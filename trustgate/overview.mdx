<p className="nt-lead">
  TrustGate is an AI agent gateway: a control plane between agents and the
  models, tools, and MCP servers they call. Point an OpenAI, Anthropic, or
  Responses client at it. Then route, authenticate, apply policy, and record
  every call — from the NeuralTrust console or the control-plane API.
</p>

## How it works

<Steps>
<Step title="Authenticate the caller">
A [application](/trustgate/access/applications) presents an API key, a JWT that
TrustGate validates against your IdP, or a client certificate. The application
never holds the provider credential.
</Step>
<Step title="Apply policy and route">
TrustGate evaluates [rate limits, budgets, tool allow-lists, and
guardrails](/trustgate/policies/overview), then the application's
[registries](/trustgate/concepts/registries) handle the upstream, with
[fallback](/trustgate/llm/routing#fallback) and
[smart routing](/trustgate/llm/routing#smart-routing) when you configure them.
</Step>
<Step title="Record the hop">
Tokens, cost, latency, and routing attempts go to traces and
[OpenTelemetry](/platform/event-schema).
</Step>
</Steps>

## Core objects

Everything in the console under **TrustGate** is one of these:

| Object | What it is |
|---|---|
| **[Gateway](/trustgate/concepts/gateways)** | The top-level tenant. Owns everything below. |
| **[Registry](/trustgate/concepts/registries)** | An upstream backend: an LLM provider or an MCP server. |
| **[Application](/trustgate/access/applications)** | The calling application's identity. Owns routing and credentials. |
| **[Auth](/trustgate/concepts/auth)** | An API key, a JWT TrustGate validates against your IdP, or a client certificate. |
| **[Policy](/trustgate/policies/overview)** | Rate limits, budgets, tool governance, guardrails, and other controls. |

## Request path

```text
client ──▶ /{consumer_slug}/v1/chat/completions
              │  X-AG-API-Key
              │  X-AG-Gateway-Slug (Private only)
              ├─ resolve gateway + application + policies
              ├─ apply policies (rate limit, budgets, guardrails, …)
              ├─ route across the application's registries (+ fallback)
              ├─ forward to the provider adapter
              └─ export telemetry → OpenTelemetry
```

The client names a **model** or uses `auto`. It does not send a provider URL or
key. [Architecture](/neuraltrust/deployment/architecture) covers the full lifecycle.

## FAQ

<AccordionGroup>
<Accordion title="Can I move an existing OpenAI or Anthropic client?">
Yes. Change the base URL and replace the provider credential with a TrustGate
application credential. TrustGate accepts OpenAI Chat Completions, Responses,
Anthropic Messages, and Google Gemini formats, then adapts the request for the
selected upstream. Start from the connection snippet on the application **Connect**
tab.
</Accordion>
<Accordion title="API key or JWT?">
Use an API key when the application holds a secret of its own. Or send a JWT
your IdP issued — TrustGate validates it against the IdP and, through the
application's auth binding, admits only the client ids you list. Either way the
application's routing decides registries and models; token claims never do. See
[Authentication](/trustgate/concepts/auth).
</Accordion>
<Accordion title="Can TrustGate run in my environment?">
Yes. Hybrid keeps the data plane in your network. External runs the full
platform yourself. SaaS hosts both planes. Compare models in
[Deployment](/neuraltrust/deployment/overview).
</Accordion>
<Accordion title="Do applications need the provider's credentials?">
No. Provider credentials stay on the registry. Applications authenticate as a
application. Rotate application keys separately from provider keys.
</Accordion>
</AccordionGroup>
