Every application that calls a model or a tool needs the same things: a
credential it should not hold, a limit on what it may spend, a rule about what it
may say and do, and a record of what happened. TrustGate provides those once, in
front of every provider and every MCP server, so no application carries them
itself.

Point a client at the gateway instead of at the provider. It keeps speaking the
API it already speaks. The gateway authenticates it as an **application**, applies
the **policies** attached to it, **routes** to a registry entry using that entry's
credential, and records the hop.

## What you operate

Five objects, each answering one question. Most confusion about the product
comes from expecting one of them to answer another's.

| | |
|---|---|
| **[Gateway](/trustgate/concepts/gateways)** | Where traffic physically goes. Everything else belongs to one. |
| **[Registry](/trustgate/registry/overview)** | What the gateway may reach — model providers, MCP servers — and with whose credential. |
| **[Application](/trustgate/access/applications)** | What your team built, and what it is allowed to use. |
| **[Access](/trustgate/access/overview)** | Which people reach which servers. |
| **[Policy](/trustgate/policies/overview)** | The rules for traffic that is already allowed. |

SaaS hosts everything. **Hybrid** keeps the data plane — and every prompt — inside
your network while the console still manages it. Compare in
[Deployment](/neuraltrust/deployment/overview).
