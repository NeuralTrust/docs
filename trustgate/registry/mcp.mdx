**Registry → MCP** lists every MCP server this gateway can route tools and
resources from. Some come from the catalog, some you register yourself, and they
differ mainly in **who supplies the credential**.

## Who holds the credential

This is the decision that shapes everything else about an MCP entry.

| Kind | Who signs in | What an admin does |
|---|---|---|
| **Built-in** | Each user, with their own account | Nothing. Users install the server themselves from the Portal. |
| **Setup required** | A shared credential you supply | Add the credential before anyone can use the server. |
| **Optional config** | Each user, unless you configure a shared instance | Nothing, or configure one shared instance for everyone. |

A card that reads **Setup required** is not broken — it is waiting for you. Until
the credential is there the server is visible and unusable.

The **Installation** each user performs on a built-in server creates that
server's default instance the first time it happens. You will see it appear
without having made it.

## Installing a catalog server

**Add MCP** opens the catalog. Choosing a server opens **Install**, which asks
for:

| Field | Notes |
|---|---|
| **Instance name** | How you will recognise it later — `Linear – Production`. |
| **Authentication** | **API key** for one shared key, or **OAuth**. |

When the server uses OAuth, one more choice follows:

- **User account** — each person connects their own account the first time they
  use the server. Nobody shares a credential, and what each person can reach
  upstream is whatever their own account can reach.
- **Shared account** — machine-to-machine OAuth. You supply the client ID and
  secret, and every caller acts as that one identity.

Some providers require a pre-registered OAuth app rather than dynamic
registration; the panel says so and asks for the client ID, and the secret when
one applies.

A server that is one URL with one sign-in holds a single instance, and the panel
tells you so rather than offering an **Add instance** that would do nothing.

## Registering your own server

**Custom MCP** registers a server the catalog does not have. **Source** decides
what you are pointing at:

### An MCP server URL

An `http(s)` streamable-HTTP MCP endpoint, plus a name and an optional
description that shows on the card.

### An OpenAPI document

TrustGate can turn an existing HTTP API into MCP tools. Give it a URL to an
OpenAPI 3.x document it can fetch, and optionally an **API base URL** that
overrides `servers[0]` from the spec.

**Validate OpenAPI** has to pass before you can save. It reports which stage
failed — **fetch**, **parse** or **compile** — and on success shows the version,
how many tools the document produced, and the base URL it resolved. The tool
count is the useful number: a document that compiles to far fewer tools than you
expected usually has operations the spec does not describe well enough to expose.

### Authentication

| Mode | What the gateway sends |
|---|---|
| **None** | Nothing. |
| **Static header** | A header name and value you supply, the same for every caller. |
| **OAuth (forwarded)** | Each user connects their own account. Registration is **Automatic (DCR)** where the server supports it, otherwise **Manual**. |
| **Client credentials** | A client ID, secret and token URL; every caller acts as that identity. |

Manual OAuth registration asks for the client ID, **Authorize URL** and **Token
URL**, and optionally scopes, an [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707)
resource indicator, and whether the token endpoint takes the secret as
**client secret basic** or **client secret post**.

On an edit, secret fields read *leave blank to keep current*. Blank means keep —
you will not silently clear a stored credential by not retyping it.

A server that authenticates with the **caller's own token** cannot be switched to
another mode from this panel, and it says so.

## What users can install for themselves

A gateway's Store can be **Open** — people install anything in it — or
**Curated**, where they install from a selection. That mode is a gateway setting;
Registry shows which one is in force.

On a curated gateway, when someone wants a server outside their selection they
raise a **request**, and pending requests appear in Registry with the server, the
requester and when they asked. **Approve** grants that server to them; **Deny**
does not. Decided requests move to history.

Approving grants the server to the person who asked — it does not open the server
to everyone.

## Access is set elsewhere

The **Access** tab in a server's Instances panel is deliberately empty, and says
so: who may use a server is decided on the [Access](/trustgate/mcp/access) page.
Applications that route through a server are listed there too, and are bound from
the Applications side rather than here.

## Tools

An MCP entry exposes whatever tools its server advertises. What an application is
allowed to *call* is a policy question, not a registry one — see
[tool governance](/trustgate/policies/tool-governance).
