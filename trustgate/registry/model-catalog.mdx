These are the providers the gateway knows how to talk to. Anything not listed
connects through **OpenAI Compatible**, which is the entry for self-hosted models
and vendors that expose an OpenAI-shaped API.

The **format** column is the wire protocol the gateway translates to. It matters
in exactly one situation: a provider speaking the `openai` format accepts an
OpenAI-shaped request unchanged, so moving traffic between two of them is a
routing change and nothing else.

## Notes worth having before you connect

**Azure OpenAI** is the one that catches people out. It is deployment-scoped
rather than model-scoped: the endpoint and API version you enter decide which
models exist, so a model missing from the picker is usually a missing deployment
on the Azure side rather than anything wrong here.

**Vertex AI** and **Bedrock** authenticate as a cloud identity rather than with a
product key, which means their permissions are managed in GCP and AWS. A model
that fails only for some calls is usually an IAM problem, not a gateway one.

**OpenAI Compatible** trusts you about the base URL. Nothing validates that the
endpoint behind it actually implements the whole API, so test the connection
before you route anything real through it.

Each provider entry can hold several [instances](/trustgate/registry/overview#instances),
which is how you keep production and staging keys — or two Azure deployments —
apart without a second gateway.
