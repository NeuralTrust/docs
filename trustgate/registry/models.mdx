A model provider entry gives the gateway somewhere to send inference, and the
credential to send it with. Catalog providers know their own connection details;
an OpenAI-compatible endpoint needs a base URL as well.

## What a provider needs

Most take a **name** and an **API key**. The name is not cosmetic — it is what
appears in routes and in every trace, so `openai-prod` will serve you better than
`OpenAI` the first time two entries exist.

Some providers do not authenticate with a single key:

| Provider | What it needs |
|---|---|
| **Azure Foundry** | The Azure endpoint, an **API surface**, and an API key, a service principal (tenant, client ID, client secret), or **Managed identity**. See the note below — **API version** applies to only one of the four surfaces. |
| **Amazon Bedrock** | **Access key** — access key ID, secret access key and region, plus a session token for temporary credentials — or **Assume role** with a role ARN. An application with a Bedrock entry also answers native [Bedrock Runtime](/trustgate/endpoints/bedrock-runtime) calls from AWS SDKs. |
| **Vertex AI** | A GCP service-account JSON, uploaded or pasted. Project ID is read from the file. |
| **IBM watsonx.ai** | An IBM Cloud API key, the region of the watsonx.ai Runtime and a project ID. The gateway trades the key for IAM tokens and renews them itself. See [Setting up IBM watsonx.ai](#setting-up-ibm-watsonx-ai). |
| **Custom Model** | A base URL, and whatever that endpoint expects, including nothing. **Custom header** takes a Header Name and a Value. |

<Note>
**Azure Foundry routes through one of four API surfaces**, chosen per instance:

| Surface | What it targets |
|---|---|
| **Azure OpenAI deployments** (default) | The classic deployments path, with **API version** in the query string. |
| **Foundry OpenAI v1 chat** | Microsoft Foundry's OpenAI-compatible chat completions surface. |
| **Foundry OpenAI v1 responses** | Foundry's OpenAI-compatible Responses surface. |
| **Foundry Anthropic messages** | Foundry's Anthropic-compatible Messages surface. |

**Foundry OpenAI v1 chat** and **Foundry OpenAI v1 responses** call
`/openai/v1/...`, and **Foundry Anthropic messages** calls
`/anthropic/v1/messages`. All three ignore **API version** entirely; only
**Azure OpenAI deployments** uses the classic deployments path and needs it. Pick the surface that matches how the deployment was created in
Azure — it decides the path, the request and response shape, and the
authentication headers the gateway sends, not just which model names resolve.
</Note>

Keys are stored encrypted and never shown again. On an existing entry, leaving
the key blank keeps the stored one; typing a new one replaces it. Rotating a
credential is therefore an edit on the entry, and nothing downstream has to
change — applications, policies and access all point at the entry, never at the
secret.

### Amazon Bedrock permissions

The credentials of a Bedrock entry need three groups of IAM actions. Only the
first is required to serve traffic; the other two change what you see and what
gets priced.

| Group | Actions | What it is for |
|---|---|---|
| **Runtime** (required) | `bedrock:InvokeModel`, `bedrock:InvokeModelWithResponseStream` | Calling models. Without them requests fail. |
| **Model list** (recommended) | `bedrock:ListFoundationModels`, `bedrock:ListInferenceProfiles`, `bedrock:GetFoundationModelAvailability` | Narrows the model list to the models these credentials can invoke. Without them the list shows the full catalog, including models your account cannot invoke. Invoking is unaffected. |
| **Cost lookups** (optional) | `bedrock:GetInferenceProfile`, `bedrock:GetProvisionedModelThroughput` | Pricing a call to an application inference profile or a provisioned throughput. Without them that usage is recorded without a cost. Other models are unaffected. |

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BedrockInvoke",
      "Effect": "Allow",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream"
      ],
      "Resource": "*"
    },
    {
      "Sid": "BedrockModelCatalog",
      "Effect": "Allow",
      "Action": [
        "bedrock:ListFoundationModels",
        "bedrock:ListInferenceProfiles",
        "bedrock:GetFoundationModelAvailability"
      ],
      "Resource": "*"
    },
    {
      "Sid": "BedrockCostLookup",
      "Effect": "Allow",
      "Action": [
        "bedrock:GetInferenceProfile",
        "bedrock:GetProvisionedModelThroughput"
      ],
      "Resource": "*"
    }
  ]
}
```

<Note>
**Test connection** succeeds when a model list permission is missing, and shows
a warning naming each missing permission. A change in IAM takes effect within
about a minute, or immediately after **Test connection**.
</Note>

### Setting up IBM watsonx.ai

An IBM watsonx.ai entry calls the watsonx.ai Runtime in one IBM Cloud region.
It authenticates with an IBM Cloud API key: the gateway exchanges the key for
an IAM bearer token, reuses that token across calls and fetches a new one
before it expires, so nothing needs rotating every hour.

Set up three things in IBM Cloud first:

1. **A watsonx.ai Runtime instance** in the region you will call. The free Lite
   plan is enough to try the integration.
2. **A project with that instance associated.** In the project, open
   **Manage → Services & integrations → Associate service**. Without the
   association, calls fail even with a valid key. Copy the project ID from
   **Manage → General**.
3. **An API key**, from **IBM Cloud → Manage → Access (IAM) → API keys**. The
   key acts as the user or service ID that owns it, so that identity must be a
   collaborator on the project.

| Field | What it is |
|---|---|
| **IBM Cloud API key** | The key from step 3. The gateway sends it only to IBM Cloud IAM (`iam.cloud.ibm.com`); calls to watsonx.ai carry the token. |
| **Region** | Where the Runtime instance lives: Dallas (`us-south`), Frankfurt (`eu-de`), London (`eu-gb`), Tokyo (`jp-tok`), Sydney (`au-syd`) or Toronto (`ca-tor`). |
| **Project ID** | The project from step 2. Every call runs, and is billed, in this project. A project named in a request body is ignored. |
| **API version** (Advanced) | The watsonx.ai API version, as a `YYYY-MM-DD` date. Defaults to `2025-10-01`. |
| **Base URL** (Advanced) | Replaces the regional endpoint, for a private or dedicated one. |

Clients call the entry in the dialect they already speak, as described in
[Connect](/trustgate/llm/connect), and TrustGate translates to the watsonx.ai
chat API. Streaming and tool calls work. Embeddings, images and audio are not
served. Model names are watsonx.ai's own, such as `ibm/granite-4-h-small` or
`meta-llama/llama-3-3-70b-instruct`.

**Models.** The list is the region's own. Regions serve different models, so a
Frankfurt entry lists fewer than a Dallas one. Withdrawn models are left out and
deprecated ones are labelled.

**Pricing.** List prices come from models.dev, which publishes them for only
some watsonx.ai models. The others are listed without a price, and their
traffic is recorded without a cost until you add a
[model override](#contract-pricing): `ibm/*` covers the Granite family.

<Note>
**Test connection** checks the API key and the region: it obtains an IAM token
and lists the region's models with it. It does not check the project ID. A
wrong project, or one without the Runtime associated, shows up as IBM's error on
the first call.
</Note>

Not supported yet: deployment spaces (`space_id`), the IBM Cloud private IAM
endpoint, and the Mumbai region, which runs on AWS with its own sign-in.

## Contract pricing

Cost in Analytics, on every trace, and in any budget policy is only as true as
the rates behind it. By default TrustGate prices traffic at list rates. If you
negotiated something else, the reporting is wrong until you say so here.

| Setting | Meaning |
|---|---|
| **List discount** | A percentage off list, applied to every model on this provider. |
| **Model override** | A model slug with explicit input and output rates, in USD per million tokens. A trailing `*` covers a family, so `gpt-4o-mini*` catches the variants. |

Overrides win wherever they match; the discount covers everything else. A flat
contract needs only the discount. Add overrides for the models priced outside it.

This matters beyond reporting: a budget policy that stops spend at a threshold is
counting with these numbers.

## Instances

A provider entry holds as many instances as you need — production and staging
keys, two Azure deployments, one key per cost centre. Each is configured and
tested on its own, and each is selectable independently when routing or an
application picks a destination.

## Prompt caching

Providers differ in what they cache on their own and what a request has to
mark. Anthropic and Bedrock cache only what the client marks, OpenAI and Azure
cache long prefixes automatically, and Mistral takes a cache key. TrustGate
carries the client's markers to whichever provider answers, and prices cache
reads and writes at the rates above. [Prompt caching](/trustgate/concepts/prompt-caching)
has the full table, including which Bedrock models accept a cache checkpoint.

## Every provider

These are the providers the gateway knows how to talk to. Anything not listed
connects through the **Custom Model** button, the flow for self-hosted models
and vendors that expose an OpenAI-shaped API.

The **format** column is the wire protocol the gateway translates to. It matters
in exactly one situation: a provider speaking the `openai` format accepts an
OpenAI-shaped request unchanged, so moving traffic between two of them is a
routing change and nothing else.
