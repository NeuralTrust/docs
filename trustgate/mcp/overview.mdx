---
title: "MCP Gateway"
description: "One endpoint in front of every MCP server an application may use. The agent sees one catalogue; the gateway decides what is in it, who signed in upstream, and what gets recorded."
---

An agent connects to **one** URL and sees one catalogue of tools, prompts and
resources. Behind it, the gateway fans each listing out to the MCP servers the
application is allowed to use, merges the answers, and routes each call to the
server that owns it. The agent never learns an upstream address and never holds
an upstream credential.

That is the whole design. Everything else on this plane is a consequence of
putting the gateway, rather than the agent, in charge of three things: **which
servers** are visible, **whose account** reaches each one, and **what is
recorded**.

## Which servers an agent sees

An application's surface is exactly the MCP servers bound to it, narrowed by its
tool restrictions. It is the same for every caller the application admits. To give
two audiences different tools, make two applications — the surface is a property
of the application, not of who is calling.

People using the [Employee portal](/trustgate/mcp/store) are the exception: their surface is
per person, made of what they installed, bounded by [Access](/trustgate/access/overview).

### Tool names

With one server bound, tools keep their upstream names. With several — or on a
per-instance Employee portal install — names are prefixed with a stable hash of the
registry, so `search` on two servers does not collide. The readable part is kept
to 26 characters and the whole name under 64. The name is stable for as long as
the registry exists; a client that cached names from before a server was added
should re-list, and the gateway tells it to.

### When an upstream is down

**Fail mode** on the application decides: **open** skips the unreachable server
and serves the rest, naming the skipped server's cause if nothing at all was
reachable; **closed** fails the call. Open is the right default for an
interactive agent; closed for anything where a partial tool list would be worse
than no answer.

## Whose account reaches upstream

This is the decision that shapes an MCP application, and it is set per server on
the [registry entry](/trustgate/registry/mcp):

| Upstream auth | Who the server sees |
|---|---|
| **None** / **Static header** / **Client credentials** | The gateway, as one identity, for every caller. |
| **Forwarded**, account per caller | Each caller, as themselves, after connecting their account once. |
| **Forwarded**, shared account | One account an administrator connected on the entry, for every caller. |
| **Caller's own token** | Whatever identity the caller already carried. |

An account per caller is how a ticket tracker or a repo host keeps its own
permissions and its own audit trail: the gateway vaults one credential per person
per server instance, refreshes it, and re-asks for consent only when a grant can
no longer be refreshed. Two people installing the same server never share a
credential.

A call for someone who has not connected yet does not fail opaquely. It returns a
**consent required** error carrying a connect link and a cause — never connected,
token expired without refresh, refresh rejected, and so on — so the agent can
show the link and the person signs in once.

Machine callers authenticating with an API key carry no token of their own. On a
shared-account server they use that account like everyone else. On a per-caller
server they have to name the person the call is for — see
[acting for end users](/trustgate/mcp/end-users) — because the key on its own has
no account there; the call is refused with a message saying so rather than
falling back to someone else's. For modes that need a caller token they get an
error naming the fix rather than a silent no-op.

## The gateway's own tools

Every MCP application with a server bound also lists a few tools the gateway
implements itself, marked as plumbing so a model does not mistake them for
capabilities:

- **`trustgate_list_tools`** — a server-by-server inventory with each server's
  state: ready, needs connect (with the connect tool to call), unavailable, or no
  tools after restriction.
- **`trustgate_connect_<provider>`** — one per forwarded-auth server still waiting
  on an account; returns the connect link the agent should show.
- **`trustgate_store_search`**, **`trustgate_store_install`**,
  **`trustgate_store_uninstall`** — on the [Employee portal](/trustgate/mcp/store)
  endpoint only. The other two are there as well: the portal is an MCP surface
  like any other.

## Agents authenticate to the gateway

The MCP plane is an OAuth2 authorization server for the agents connecting to it,
with dynamic client registration and PKCE. An agent registers, obtains a token,
calls the endpoint, and completes a one-time connection when a downstream server
needs per-user authorization. Machine callers use the application key instead.

[Connect an agent](/trustgate/mcp/connect) covers both paths — an agent with its
own MCP client, and your own code through the TrustGate SDK.

## Keeping catalogues fresh

The gateway pushes a *tools changed* notification when a stream opens and whenever
the caller's surface changes — a server bound or unbound, a restriction edited, an
account connected or revoked, an Employee portal install or a grant. Clients that honour it
re-list without reconnecting.

## Limits

An upstream JSON response or single event is capped at 8 MiB; a catalogue listing
at 16 MiB and 10,000 entries. Closing a session cancels its in-flight requests.
