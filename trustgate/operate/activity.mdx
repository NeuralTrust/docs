title: "Activity"
description: "Every request the gateway handled, with what it decided and why. Three views of the same record: one request, one trace, one conversation."
---

Activity is the record. Every call through the gateway — an LLM request, an MCP
tool call — becomes one row with what was asked, what was answered, which
policies ran, and what they decided.

## Three views

| View | One row is | Use it for |
|---|---|---|
| **Requests** | One HTTP request. | The default. Find the call, read its decision. |
| **Traces** | Everything that happened under one trace id: LLM calls, tool calls, policy invocations, as a waterfall. | An agent turn that made several calls — see them together and in order. |
| **Conversations** | One session. | A chat client's back-and-forth as one thread. Needs a [session id](/trustgate/observability/end-user-attribution#grouping-a-conversation). |

## Reading a request

The row tells you the protocol, the application, who it was for, the operation —
for MCP, the actual tool called — the provider, latency, tokens, cost, and
whether anything flagged it. **Upstream error** on a row that returned `200` is
worth knowing: the gateway accepted the request, but the tool or provider behind
it failed. Open it for the error.

Opening a request shows four tabs:

- **Request** — protocol, method, model, path, messages searchable by text or as
  JSON; for MCP, the method, operation, server, tool and upstream tool. Plus
  **who**: the authenticated principal and how it authenticated (API key,
  external IdP, gateway login, mTLS), and separately the end user a client
  application declared, marked as such because it is unverified.
- **Response** — status, latency, completion tokens, finish reason, body.
- **Policies** — the chain that ran, in order, each with its decision, latency,
  bytes in and out, and for detectors whether they passed, flagged, errored or
  were not inspected and why. Plus the latency split between gateway, policies
  and provider.
- **Metadata** — tokens and cost broken into prompt and completion, and a link to
  the matching TrustGuard activity when the request carried a correlation.

The **Policies** tab is where "why was this blocked" gets answered. A decision
without a policy in the chain means the gateway itself refused — routing,
restriction, authentication — and the response body says which.

## Finding things

Filter by application, provider — including providers on this gateway versus the
wider catalogue — user, protocol, status, and **flagged only**. Search matches
messages, user identifiers and tool names.

When you arrive from Agent Runtime with a trace id, Activity shows only the
linked request and says so; **Show all requests** widens it again.

## What is not here

Raw prompts and responses are stored separately from the metadata that alerts and
analytics run on, keyed by trace id, and on a Hybrid deployment they never leave
your network. Activity reads both; the event stream that feeds
[Analytics](/trustgate/operate/analytics) and alerts reads only the metadata.
