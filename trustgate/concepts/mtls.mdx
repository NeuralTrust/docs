title: "mTLS"
description: "Authenticate callers to TrustGate with a client certificate — CA, optional allowlists, per-application certificate subjects, and X-Forwarded-Client-Cert when TLS terminates in front of the gateway."
---

**mTLS** is a application [auth](/trustgate/concepts/auth) type. The caller presents a client
certificate. TrustGate verifies it against your CA and optionally against CN, DNS SAN, or
SHA-256 fingerprint allowlists on the CA, then against the application's own **Allowed
certificate subjects**. It works on the LLM proxy plane and on the MCP plane.

This is **client → TrustGate**. It is not how TrustGate authenticates to an upstream MCP
server, and it is not a TrustGuard evaluate-API method.

The **Machine identity** create form offers **IdP (JWT)** anchors only. Create the CA anchor
with the [Admin API](/trustgate/api/credentials), then attach it to a application; an attached
CA shows on the application as **Client certificate (mTLS)**.

## Quick path

1. Issue a client certificate from a CA you control. Keep the CA PEM.
2. `POST /v1/gateways/{gateway_id}/auths` with `type: mtls` and `config.mtls.ca_cert`.
3. `POST /v1/gateways/{gateway_id}/consumers/{id}/auths/{auth_id}` on the application.
   Optionally set `auth_binding.allowed_certificate_subjects` on the application.
4. Terminate TLS in front of TrustGate (or on the process). If a proxy terminates TLS, set
   `TRUST_XFCC_FROM` to that proxy's IPs and forward `X-Forwarded-Client-Cert`.
5. Call the proxy or MCP plane with the client certificate. A valid cert and matching
   allowlists authenticate as that application.

## What TrustGate checks

Verification uses `x509` client-auth EKU against `ca_cert`. Empty allowlists mean “any
cert from this CA”.

| Field | Required | Meaning |
|---|---|---|
| `ca_cert` | Yes | PEM CA bundle used as the trust roots. |
| `allowed_common_names` | No | Subject CN must be in this list. |
| `allowed_dns_names` | No | At least one DNS SAN must be in this list. |
| `allowed_fingerprints` | No | SHA-256 of the leaf DER. Hex, optional colons, case-insensitive. |

These lists live on the CA anchor and apply to every application that attaches it. To narrow one
application further, set `auth_binding.allowed_certificate_subjects` on the
[application](/trustgate/access/applications#auth-binding): the CN or one of the SAN DNS names
must be in that list, or the request gets `403`. An empty list accepts any certificate the
CA verified.

The principal **subject** is the certificate CN, or the first DNS SAN if CN is empty.
Telemetry records `trustgate.principal.method` = `mtls`. An MCP application entered with a
certificate runs as principal `app:<consumer_id>`.

Auth resolution differs per plane:

| Plane | Order |
|---|---|
| MCP (`:8082`) | **client certificate → bearer token → API key**. A certificate, when present, is the credential checked. |
| LLM proxy (`:8081`) | **API key header → client certificate → bearer token**. The certificate is consulted only when the request carries no `Authorization` header and the application has an mTLS auth attached; an explicit credential wins. |

## How the certificate arrives

TrustGate's HTTP planes listen in plaintext. On both planes the leaf comes from one of:

| Source | When it is used |
|---|---|
| TLS peer certificate | The process terminated TLS and the handshake presented a client cert. |
| `X-Forwarded-Client-Cert` | The **immediate** peer IP is in `TRUST_XFCC_FROM`. |

`TRUST_XFCC_FROM` is a comma-separated list of IPs or CIDRs. If it is empty, TrustGate
**ignores** XFCC — a client cannot smuggle a cert header, and a header from a peer outside
the list is rejected.

The header is Envoy-style: a `Cert=` element whose value is a URL-encoded PEM. Example
shape (truncated):

```http
X-Forwarded-Client-Cert: Cert="-----BEGIN%20CERTIFICATE-----%0A..."
```

<Warning>
Only put the TLS-terminating proxy in `TRUST_XFCC_FROM`. Anyone in that set can present
an arbitrary client certificate as if it were on the wire.
</Warning>

## Create and attach

Admin JWT or [machine credentials](/trustgate/api/credentials) on the Admin plane:

```http
POST /v1/gateways/{gateway_id}/auths
Authorization: Bearer <admin-jwt>
Content-Type: application/json
```

```json
{
  "name": "partner-mtls",
  "type": "mtls",
  "config": {
    "mtls": {
      "ca_cert": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----",
      "allowed_common_names": ["partner-app"],
      "allowed_dns_names": ["client.partner.example"],
      "allowed_fingerprints": ["aa:bb:..."]
    }
  }
}
```

Then attach to the application:

```http
POST /v1/gateways/{gateway_id}/applications/{consumer_id}/auths/{auth_id}
Authorization: Bearer <admin-jwt>
```

To restrict which certificates from that CA may enter this application:

```http
PUT /v1/gateways/{gateway_id}/applications/{consumer_id}
Content-Type: application/json
```

```json
{
  "auth_binding": {
    "allowed_certificate_subjects": ["partner-app", "client.partner.example"]
  }
}
```

## Where it applies

| Surface | mTLS |
|---|---|
| LLM proxy (`:8081`) | Yes. |
| MCP plane (`:8082`), inbound | Yes — the application acts as the application, or names its end users with `X-NeuralTrust-End-User` (`identity.source: app`). Interactive agents (Cursor, etc.) still need [OAuth2](/trustgate/concepts/auth) to broker login. |
| Application whose users sign in (`identity.source: platform`) | No — it needs an OAuth2 provider that can broker the login, or the built-in NeuralTrust login. |
| TrustGate → upstream MCP (`mcp_target.auth`) | No — modes are `none`, `static`, `passthrough`, `exchange`, `forwarded`, `client_credentials`. |
| TrustGuard `/v1/evaluate` | No — collector API key or service token. |
