---
title: "mTLS"
description: "A client certificate as the application's identity. The gateway verifies it against a CA you trust; the application decides which subjects from that CA get in."
---

With mTLS the caller's identity is a **certificate**. The gateway verifies it
against a certificate authority configured as a trust anchor, applies any
allowlist on that anchor — common names, DNS names, fingerprints — and then the
application's own **Allowed certificate subjects**. A certificate that passes all
of that authenticates as that application, on both planes.

This is the caller's identity **to the gateway**. It is not how the gateway
authenticates to an MCP server, which has its own modes, and it is not a
TrustGuard method.

## Who is the subject

The principal is the certificate's common name, or its first DNS SAN when the CN
is empty. That is what Activity shows, and what a subject allowlist matches.

Allowlists on the CA anchor apply to every application that selects it; the
application's own subject list narrows further. Both empty means "any certificate
this CA signed", which is the right setting exactly when the CA is dedicated to
callers of this gateway and wrong otherwise.

## How the certificate reaches the gateway

The gateway's planes listen in plaintext, so the certificate arrives one of two
ways: as the TLS peer certificate when the gateway process terminated TLS itself,
or in an `X-Forwarded-Client-Cert` header when a proxy in front of it did.

The header is trusted **only** from peers listed in `TRUST_XFCC_FROM`. Empty means
never: a client cannot smuggle a certificate in a header, and a header from an
unlisted peer is rejected.

<Warning>
Put only the TLS-terminating proxy in `TRUST_XFCC_FROM`. Anyone in that set can
present any client certificate as though it had been on the wire.
</Warning>

## Which credential wins

The planes resolve differently when a request could carry more than one:

| Plane | Order |
|---|---|
| **MCP** | Certificate, then bearer token, then API key. A certificate present is the credential checked. |
| **LLM** | API key, then certificate, then bearer token. The certificate is consulted only when no `Authorization` header is present and the application accepts mTLS; an explicit credential wins. |

## Where it applies, and does not

Both planes inbound, for machine callers and for an application that names its own
end users. Not for an application whose users sign in themselves — a person needs
a login the gateway can broker, or the NeuralTrust one. Not for the gateway's own
calls to MCP servers or providers.

Certificate-authority anchors are created through the Admin API today; the
console's Machine identity form offers identity providers. Once created, an
anchor appears on the application as **Client certificate (mTLS)** like any other
method.
