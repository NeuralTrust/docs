title: "Gateways"
description: "A gateway is the deployment your clients call, and the boundary of everything you configure. Most teams need one; a second is for a separate environment, not for separating teams."
---

A **gateway** is a running TrustGate deployment. It has two addresses your
clients call — an **LLM Gateway** URL and an **MCP Gateway** URL — and one for
people: the **Portal**, an MCP endpoint that lists the servers each person may use.

A client keeps speaking the API it already speaks: OpenAI-style requests to the
LLM URL, MCP to the MCP URL. The gateway authenticates it as an
[application](/trustgate/access/applications), applies the
[policies](/trustgate/policies/overview) attached to it, routes to a
[registry](/trustgate/registry/overview) entry with that entry's credential, and
records the hop as a trace.

## Everything belongs to one

The console shows one gateway at a time — the one in the **Gateway** selector at
the top. Registry, Access, Policies, Activity, Analytics, Playground and Settings
all read from that gateway and write to it. Switching gateway switches all of them.

| A gateway owns | |
|---|---|
| **Registry entries** | The providers and MCP servers it may reach, with their credentials. |
| **Applications** | The keys and identities that may call it. |
| **Access** | Which people reach which servers. |
| **Policies** | The rules it enforces. |
| **Traces** | Every request it handled. |
| **Settings** | Its URLs, environment label, Admin API credentials and the identity providers it trusts. |

Nothing crosses between two gateways. An application registered on one is
unknown to the other, and a policy has to exist on each gateway it should apply to.

## One, usually

Applications separate what your teams built. Access separates people. Instances
separate production keys from staging keys on the same provider. Policies
separate rules. Each axis you might reach for a second gateway to get, something
smaller already provides — without a second set of credentials to manage and a
second Activity to watch.

A second gateway is for a **genuinely separate environment**: a different
network, a different data residency, a blast radius you want walled off. Those
are the cases where "nothing crosses between two" is the feature. Give each one
an **Environment** label — production, staging, development — and it is marked as
such wherever it appears.

## SaaS or Private

The **deployment type** is chosen at creation and cannot change afterwards
without recreating the gateway.

| | Where the data plane runs | Choose it when |
|---|---|---|
| **SaaS** | NeuralTrust hosts it. Nothing to install. | Default. |
| **Private** | You run it — Docker, Kubernetes or by hand — and register its public URL, at creation or later. The console still manages it. | Prompts must not leave your network, or you need fixed capacity, no cold starts and your own SLA. |

The console is identical either way. What differs is where a request physically
goes — and that the console cannot reach a private data plane from outside your
network, so the Playground and connection tests run from a machine that can.
[Deployment](/neuraltrust/deployment/overview) covers running one.
