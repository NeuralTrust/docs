An **auth** is how a client proves it may act as a [application](/trustgate/access/applications).
Distinct from a registry's **upstream** credential (how TrustGate calls the model provider or
MCP server).

Two kinds of auth entities exist:

- **API keys** belong to one application. Issue, rotate, and revoke them on the application's
  **General** tab under **Authentication**.
- **Trust anchors** — external identity providers and mTLS certificate authorities — are
  gateway-level and shared by many applications. Manage them at **Settings → Agent Gateway →
  Machine identity**, then select one on the application under **Authentication → Identity
  provider**. Which callers of a shared anchor may enter a given application is the application's
  [auth binding](/trustgate/access/applications#auth-binding).

## Types

| Type | How the client authenticates | Typical use |
|---|---|---|
| **API Key** (`api_key`) | `X-AG-API-Key: ag_…`, `x-api-key: ag_…`, or `Authorization: Bearer ag_…` | Applications, backend agents, scheduled jobs |
| **OAuth2** (`oauth2`) | Bearer token issued by your IdP. TrustGate **validates** a token the client already holds (JWT or, with an introspection URL, opaque), or **brokers** the login (authorization code + PKCE) for MCP clients | LLM apps with an IdP token; M2M; MCP agents |
| **mTLS** (`mtls`) | Client certificate (or a trusted `X-Forwarded-Client-Cert` header) — [mTLS](/trustgate/concepts/mtls) | Machine callers on both planes |

`oidc` is a deprecated alias of `oauth2`: `type: oidc` and `config.oidc` are still accepted
on create and update, but responses always carry the `oauth2` shape.

| Protocol | Methods in the console |
|---|---|
| **LLM** | **API key**, **Identity provider** (bearer JWT validated against the IdP). |
| **MCP** | **API key**, **Identity provider**, or **NeuralTrust login** (the built-in IdP — no auth attached). A application whose users sign in needs a provider that can broker the login; a validation-only provider is refused. |

**mTLS** anchors are created with the Admin API (the console form offers **IdP (JWT)**) and
attach to applications on both planes. See [mTLS](/trustgate/concepts/mtls).

## API keys

1. Open the application → **General** → **Authentication** → **API key** → **Add API key**
   (or pick **API key** when creating the application; one key is issued on create).
2. Copy the secret once. Use it in requests or in the application **Connect** snippets.
3. **Regenerate** or **Revoke** from the same list.

Keys are prefixed `ag_`. TrustGate stores a hash; the secret cannot be recovered. Rotate by
creating a new key, updating clients, then revoking the old one.

Both planes accept the key as `X-AG-API-Key`, as `x-api-key` (Anthropic-style clients), or
as `Authorization: Bearer ag_…`. A bearer that starts with `ag_` is treated as an API key;
any other bearer goes to the OAuth2 validators. An MCP application called with an API key runs
as principal `app:<consumer_id>`, so rotating or renaming a key never strands the upstream
accounts linked to the application.

## OAuth2 setup modes

One `oauth2` entity covers every IdP pattern; the **Setup** choice decides which fields you
fill.

| Mode | When | Fields |
|---|---|---|
| **Validate tokens only (machine-to-machine)** | The caller already holds a JWT from your IdP (client credentials, certificate credentials, a user token your app obtained). No browser login. Console kind **IdP (JWT)**. | `issuer`, `audiences`; optionally `jwks_url` or inline `public_keys`, `allowed_algorithms`, `required_scopes`, `subject_claim`. |
| **Interactive login · IdP with discovery (Okta, Entra ID)** | MCP clients sign in through TrustGate's authorization-code + PKCE broker; endpoints come from `/.well-known/openid-configuration`. | Validation fields plus `client_id`, `client_secret`. |
| **Interactive login · IdP without discovery (GitHub)** | The IdP publishes no discovery metadata. | Plus `authorize_url` + `token_url` (set together); `session_mode` + `userinfo_url` for opaque, non-JWT tokens. |

`introspection_url` validates opaque tokens without session mode. HMAC algorithms (`HS*`) are
rejected: only asymmetric signatures are accepted. When `public_keys` are set, discovery is
skipped.

## Two ways to use an IdP

The same Okta or Entra tenant can back both. What differs is whether TrustGate only checks a
token or also runs the login.

| Pattern | Application | What TrustGate does | IdP app |
|---|---|---|---|
| **Validate a bearer JWT** | LLM or MCP, machine or user token | Verifies signature, `iss`, `exp`/`nbf`, `aud`, `required_scopes`; then the application's **Allowed client IDs** (`azp`, else `client_id`). Claims never select a registry or model. | Issuer + audience (no client secret). |
| **Interactive MCP login** | MCP whose users sign in | Brokers authorization code + PKCE, validates the tokens the IdP issues, keeps per-user upstream connections. **Required scopes** gate access. | Confidential client with redirect `{mcp_base_url}/oauth/callback`. |

When a request carries a bearer JWT, TrustGate picks the provider by the token's `iss` and
`aud` among the auths attached to the application's path, so one application may attach several
IdPs. Client-credentials tokens are for curl checks or M2M apps, never for interactive
agents.

## Rules for every provider

- **Audiences** is required and must match the token's `aud` claim. An `api://` resource URI
  and its bare identifier count as the same audience.
- **Required scopes** must not include `openid`, `profile`, `email`, or `offline_access`.
- Scope matching uses `scp`/`scope` **and** Auth0/Entra-style `permissions` and `roles` arrays.
- Interactive MCP: **Setup → Interactive login · IdP with discovery**, Session mode off,
  Okta app type **Web Application** (not API Services).
- **JWKS URL** can stay under **Token validation · advanced**; TrustGate resolves keys from
  the issuer when needed.
- Telemetry records `trustgate.principal.method` as `external_jwt` (your IdP's token),
  `oauth` (a gateway-brokered login), `api_key`, `mtls`, or `introspection`.
