The **OpenAI Moderation** policy sends text to
[OpenAI's Moderations API](https://platform.openai.com/docs/guides/moderation)
and records a score for every category the model returns. It either **blocks**
the call or lets it through: the Moderations API returns scores, not rewritten
text, so there is nothing for this policy to put back.

Applies to **LLM** traffic only. Text only.

<Warning>
**This policy puts a synchronous call to OpenAI in front of every inspected
leg.** What that costs depends on your region and the size of the conversation,
so measure it in your own environment rather than assuming.
</Warning>

---

## Before you configure: the OpenAI key

This policy calls OpenAI with a credential of your own, so you need a key before
it can do anything. That is the whole prerequisite — there is no resource to
create, no template to build and no permission to grant, which is what makes
this the quickest of the guardrails to stand up.

Two things worth knowing before you pick a key. The Moderations API is billed
separately from your model usage, and this policy calls it on every inspected
leg in its scope. And a key you save here is stored encrypted and never comes
back to your browser, so you cannot read it off the policy afterwards — give it
a key scoped to moderation rather than one that can also spend on completions,
and keep your own copy wherever you keep your other credentials.

## Configure the policy

Open **Policies** → **Library** → **OpenAI Moderation**.

| Field | What to choose |
|---|---|
| **Model** | The Moderations model: `omni-moderation-latest` (default) or `omni-moderation-2024-09-26`. OpenAI has retired every `text-moderation-*` model; a new write cannot select one. |
| **API Key** | An OpenAI credential of your own. Required. |
| **Inspect model responses** | Off by default, directly below **API Key** with no section heading of its own — see [Inspecting the response too](#inspecting-the-response-too). |
| **Categories** | An allow-list of categories to evaluate. Empty evaluates everything OpenAI returns. |
| **Thresholds** | A score per category, between 0 and 1. A score **at or above** the threshold blocks. |
| **Block On Flagged** | Refuses any category OpenAI itself marks as flagged, with no threshold of your own. Off when you turn it off explicitly — see the warning in [Making it block](#making-it-block) for what happens when you leave it untouched. |

Only **Model** and **API Key** have to be filled in to save. The rest is what
turns a scoring instrument into a guardrail — see
[Making it block](#making-it-block).

<Note>
**Saving validates more than "is it filled in."** The gateway rejects the
write with `422 validation_failed` for: an unknown **Model** (unless it is
exactly the model already stored on this policy); a **Categories** or
**Thresholds** key outside the 13 OpenAI defines — `harassment`,
`harassment/threatening`, `hate`, `hate/threatening`, `illicit`,
`illicit/violent`, `self-harm`, `self-harm/intent`, `self-harm/instructions`,
`sexual`, `sexual/minors`, `violence`, `violence/graphic` — again unless it is
already stored; or **Block On Flagged** explicitly set to `false` with no
**Thresholds** configured, since that policy could never block or report
anything. A model or key already stored under older rules stays editable;
only a newly introduced bad value is refused.
</Note>

### The key, once saved

**A key you save is stored encrypted and is never sent back to the browser.**
Reopen the policy and the field tells you only that a key is set; it does not
show you the key. You can replace it, and you cannot read it. Rotating means
pasting the new key over that marker, which is also the only way to correct a
key you typed wrongly.

### Inspecting the response too

**The request is always inspected** — that is not a setting, and it is one call
to OpenAI on every turn. **Inspect model responses**, the toggle directly below
**API Key**, is off by default. Turn it on and the model's answer is sent to
the Moderations API too, checked against the same **Categories**,
**Thresholds** and **Block On Flagged** as the request: a second call to
OpenAI on every turn. There is no way to inspect the response only — the
request is always inspected first.

Measure what the request alone costs you before you turn this on; it is the
call that can stop something before it reaches the model, and it is the one
this policy always makes.

A policy set up through the admin API whose plugin settings leave `stages`
unset inspects the response whenever the policy's own stages include it; the
console shows that as **Inspect model responses** turned on.

<Note>
**A streamed response is not inspected**, even with **Inspect model responses**
on, unless streaming inspection has been configured on this policy through the
admin API. From the console, only a non-streamed response is evaluated.
</Note>

### Mode and scope

Start in **Observe** and read the recorded scores before you choose thresholds.
That is not ceremony here — you cannot pick a sensible threshold for your traffic
without seeing what your traffic actually scores.

## Making it block

<Warning>
**A policy saved with nothing touched beyond Model and API Key is not inert.**
When **Thresholds** is empty and **Block On Flagged** is left untouched (not
saved as `false`), the policy defaults **Block On Flagged** to **on** — it has
to act on something, and the flagged verdict is the only signal left. Turn
**Block On Flagged** off explicitly, or set at least one threshold, if you want
a policy that only scores and never refuses.
</Warning>

Two settings decide whether a call is ever refused, and either one on its own
is enough.

**Block On Flagged** is the switch. OpenAI's own answer says whether it
considers a category flagged, and turning this on refuses anything it flags —
no number of yours to pick, and no reading of scores first. It is the quickest
way to make this policy a guardrail, and the trade is that you are accepting
OpenAI's judgement of your traffic rather than your own. Turn it off explicitly
once you would rather rely only on your own **Thresholds**.

**Thresholds** are the dial. Give a category a score between 0 and 1, and a
score **at or above** it refuses the call. This is what you want once **Observe**
has shown you how your own traffic actually scores, because the number that
matters is the one that sits between your normal traffic and what you want
refused. Setting at least one threshold also turns off the **Block On Flagged**
default above, since the policy then has something else to act on.

A category with neither a threshold nor an explicit **Block On Flagged** is
still scored and still recorded — it simply never refuses anything on its own.

The category names have to be exactly the ones OpenAI uses. The reliable way to
learn them is to run in **Observe** and read the per-category scores on the
request's **Policies** tab in **Activity** — every category OpenAI scored is
named there.

<Warning>
**A threshold of `0` blocks everything in that category.** The comparison is
*at or above*, and every score is at or above zero. A category with a `0`
threshold refuses every request that reaches this policy, whatever the content.
It is the most common way to take an application offline with this policy.
</Warning>

<Warning>
**Categories is an allow-list that also switches off thresholds.** A category
outside the list is not evaluated at all, so a threshold you set for it is never
consulted and nothing reports that it was ignored. If you list categories, list
every category you have a threshold for.
</Warning>

## How the decision is made

<Steps>
<Step title="The text is flattened and sent in one call">
On the request leg, the system prompt and the content of every message are joined
with newlines into a single string. On the response leg, the assistant's content
alone. One call, one string.
</Step>

<Step title="Scores are aggregated across the returned results">
The highest score per category wins, and a category flagged in any result counts
as flagged.
</Step>

<Step title="Each evaluated category is checked">
A category with a threshold is a violation when its score is at or above it. A
category without a threshold is a violation only when **Block On Flagged** is on
and OpenAI flagged it. **With neither, there are no violations and nothing is
ever blocked.**
</Step>

<Step title="A violation in Enforce refuses the call">
The caller gets `403`, and the response lists every category that crossed, with
the score OpenAI returned and the threshold it crossed. The wording is
`This content violates our usage policy.` A category blocked by **Block On
Flagged** rather than by a threshold of yours is listed with no threshold beside
it.
</Step>
</Steps>

### Modes and failures

| Situation | Enforce | Observe |
|---|---|---|
| A category crosses its threshold | `403`, refused, decision `block` | Decision `reported`, request continues |
| OpenAI flags a category, **Block On Flagged** on | `403`, refused, decision `block` | Decision `reported`, request continues |
| OpenAI flags a category, no threshold and **Block On Flagged** off | **Allowed**, decision `allowed` | Allowed, decision `allowed` |
| The Moderations call fails, or its response is incomplete | **`502`, refused**, decision `failed_closed` | Decision `failed_open`, request continues |
| The gateway cannot decode the request/response body before calling OpenAI | Decision `failed_open`, request continues | Decision `failed_open`, request continues |
| The policy configuration cannot be parsed | `502`, refused | `502`, refused |
| Streaming response | Not inspected | Not inspected |

On failure in Enforce the caller gets `502`, body type `guardrail_unavailable`,
with the message `This content could not be checked right now.`

Those decision names are what you read on the request's **Policies** tab in
**Activity**: `allowed`, `reported`, `block`, and — when the call to OpenAI
itself failed — `failed_open` in Observe or `failed_closed` in Enforce. Expect
`failed_closed` on a first run: a key that is wrong, revoked or out of quota
looks from here exactly like an outage at OpenAI. The event's `failure_reason`
field says which: `transport` (the call failed or timed out), `verdict_incomplete`
(OpenAI's response did not cover a category the policy asked about),
`config_invalid` (the stored settings could not be used), or `decode_failed`
(the gateway's own request or response body could not be decoded before OpenAI
was ever called).

<Warning>
**In Enforce this policy fails closed, except for one case, and there is no
setting to change either.** A revoked key, an OpenAI rate limit, a malformed
response and an outage all refuse the caller with the same `502` — the
response itself does not say which. Check the event's `failure_reason` field
before OpenAI's status page; it distinguishes `transport`, `verdict_incomplete`
and `config_invalid`. The exception is `decode_failed`: the gateway's own body
could not be decoded before OpenAI was ever consulted, so it always fails
open, in Enforce too — there is nothing OpenAI could have refused.
</Warning>

### Limits

- **It cannot mask.** There is no anonymise action; the call is blocked or it is
  not. For redaction use [TrustGuard](/trustgate/policies/trustguard-guardrail)
  or [Regex Replace](/trustgate/policies/regex-replace).
- **Inspect model responses is off by default.** The model's answer is not
  scored until you turn it on.
- **A streamed response is not inspected**, even with **Inspect model
  responses** on, unless streaming inspection has been configured on this
  policy through the admin API. Nothing is recorded for it either way.
- **Text only, and structure is lost.** Roles, tool calls, tool definitions and
  attachments are not sent — the request leg becomes one newline-joined blob. A
  detector that would care which participant said something cannot.
- **Your own system prompt is scored.** It is the first thing in that blob, and a
  security-related system prompt can score high enough to matter. Check it in
  Observe before enforcing.
- **LLM traffic only.** The policy does not apply to MCP (Model Context Protocol)
  tool calls.

## Verify the policy

Open the **Playground**, pick an application the policy applies to, and work
through these in order. Steps 2 and 3 are one loop: observe, then enforce.

<Steps>
<Step title="Control — the path works at all">
```
hello, write me a short greeting
```

Expect a normal reply and the decision **`allowed`**. If this fails, the problem
is the application, the model or the key — not the thresholds. Fix it before
going on.
</Step>

<Step title="Observe — learn what your traffic scores">
Leave the policy in **Observe** and send real prompts, including ones you expect
to be borderline. Then open **Activity**, open each request, and read the
per-category scores on its **Policies** tab.

You are looking for two numbers: how high your acceptable traffic scores, and how
high the traffic you want refused scores. A threshold between them is the only
one worth setting. Take the exact category names from that tab too.
</Step>

<Step title="Enforce — confirm a violation is refused">
Set a **Threshold** between the two numbers you just read, or turn on **Block On
Flagged**, switch the policy to **Enforce**, and resend the prompt that scored
above it.

Expect the decision **`block`** and a `403` naming the category and the score.
Then confirm the model was never called: open the request in **Activity**, go to
its **Policies** tab, and read **Aggregated Latency**. The **Provider** row
should show no time at all. That the provider leg is empty is the evidence that
matters.

If the same prompt is allowed, the category you set a threshold for is not the
one that scored — or it is missing from **Categories**, which stops it being
evaluated at all.
</Step>
</Steps>

Every decision is recorded on the request in **Activity**, in Observe mode too:
open the request and read its **Policies** tab, where each policy in the chain
shows its decision and what it found. The
[event schema](/platform/event-schema) documents the underlying fields if you
need to match on them from an alert.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Nothing is ever blocked, scores look right | **Block On Flagged** was explicitly turned off, and no **Threshold** is set | Turn one back on — a policy where both are simply left untouched already blocks on the flagged verdict by default |
| A threshold is set and still nothing blocks | The category is not in **Categories**, so it is never evaluated | Add it, or clear **Categories** to evaluate everything |
| Every request is refused with `403` | A threshold of `0`, or one far below what normal traffic scores | Raise it; read the scores in Observe first |
| `502` on every request, decision `failed_closed` | The Moderations call is failing — wrong or revoked key, rate limit, or an outage | Check the event's `failure_reason` field, then replace the key or check OpenAI's status |
| The policy will not save | **API Key** is empty | It is required |
| Responses are never inspected | **Inspect model responses** is off, which is the default | Turn on the **Inspect model responses** toggle, below **API Key** |
| Streamed responses are never inspected | Streaming inspection is not enabled from the console | Expected; only a non-streamed response is inspected, or configure streaming inspection on the policy through the admin API |
| High scores on benign traffic | The system prompt is part of the scored text | Read it in Observe and account for it in the threshold |
| The saved key cannot be read back | It is stored encrypted and never returned to the browser | Expected — replace it rather than reading it, and keep your own copy |
| MCP tool calls are never inspected | This policy sees chat traffic only | Use [TrustGuard](/trustgate/policies/trustguard-guardrail), which covers MCP too |
