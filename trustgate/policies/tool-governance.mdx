---
title: "Tool governance"
description: "Shape which tools a model sees and how often any tool may run — for LLM function calling and for MCP tool calls."
---

Applies to **LLM** for allowlisting and injection; **LLM and MCP** for per-tool
rate limits.

Which MCP servers and tools an application may reach at all is set on the
[application](/trustgate/access/applications#what-it-may-use). These policies
govern the tools on the request path.

## Tool Allowlist

Filters the tools a **client** sends on an LLM request against glob patterns
before the model sees them — `github/*`, `search_*`. Deny wins over allow. When
filtering removes every tool you choose what happens: reject the request
(default), send an empty tool list, or strip the tool fields entirely.

The gateway refuses to filter ambiguously. A body that carries the tool fields
twice, or in a different case, is rejected rather than guessed at; a body it
cannot decode for its wire format is rejected too. Observe mode records what
enforce would have done and rewrites nothing.

## Tool Injection

Adds gateway-defined function tools to the outbound request so the model can
call them. It only adds; it never removes a client's tools. When an injected
name collides with one the client sent, **On conflict** decides: the gateway's
wins (default), the client's wins, or the request is rejected.

Each injected tool is a name, an optional description — which is what the model
reads when deciding whether to call it — and an optional parameter schema.

## Per-Tool Rate Limiter

Counts **actual tool executions**, not HTTP requests, and caps them per tool
pattern over one or more windows — `execute_code*` at 60 a minute and 500 an
hour. The first rule whose pattern matches wins.

When a window is exceeded: **reject** the call (the only option on MCP, where the
gateway itself is the caller), **inject an error result** into the LLM response,
or **strip the tool** from the next request.

### One execution, counted twice

A tool an agent runs through MCP shows up twice at the gateway: once as the
`tools/call` that executes it, and again as the tool-result message in the next
LLM request. On a policy attached to one application the two are separate
budgets, which is correct — a per-application limit is a promise about that
application. On a **gateway-wide** policy they share one counter and the
execution is charged twice unless the agent correlates them by sending the LLM
`tool_call_id` in the `tools/call` metadata.

The `tools/call` is always charged; the id only cancels the second observation,
so repeating it buys nothing. Attaching the policy per application avoids the
question entirely.
