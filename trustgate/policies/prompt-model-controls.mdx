---

**Prompt Management** catalog policies reshape the LLM request body on `pre_request`.
Create them under **Policies** → **Catalog**, or attach them from a consumer **Policies**
tab. Scope each policy **gateway-wide** or **targeted**.

| Policy in the catalog | Slug | What it does |
|---|---|---|
| **[Prompt Template](#prompt-template)** | `prompt_template` | Auto-inject system prompts and/or render client-referenced named, versioned templates. |
| **[Prompt Compression](#prompt-compression)** | `prompt_compression` | Minify JSON, strip ANSI, collapse whitespace — deterministic, fail-open. |

Protocol: **LLM** only.

To **restrict which models** a consumer may call, use the consumer **Routing** tab
(**Filter by available models** / **default model**) — not a catalog policy. See
[Model resolution](/trustgate/routing/model-resolution).

## Prompt Template

**`prompt_template`** rewrites the chat body on `pre_request`, substituting
[Mustache](https://mustache.github.io/)-style `{{placeholders}}` (v1 engine: **mustache**
only).

It does two unrelated jobs, and the console asks which one you want before showing you
any fields:

| What you want | Who it serves | Backend |
|---|---|---|
| **Add a system prompt to every request** | Your platform team. The gateway injects it; callers send their request unchanged and never see it. | `inject_templates` |
| **Publish a prompt library clients can invoke** | Your API's callers. They ask for a template by name and version. | `named_templates` |

A policy may carry both at once, and the gateway runs each. The console edits one at a
time and saves both, so config the panel is not showing is never dropped; it tells you
when the other side has templates.

### Recipe: inject a different system prompt per tenant

Give every caller the same instructions, with one value that changes per request — the
tenant, the end user's id, a plan tier — read from a header or a JWT claim.

<Steps>
  <Step title="Create the policy">
    **TrustGate → Policies → Catalog → Prompt Template**, then pick **Add a system prompt
    to every request**.
  </Step>
  <Step title="Write the template">
    Give it an **Identifier** (this shows up in traces, not in the prompt) and write the
    **Content**, marking the parts that vary with `{{double_braces}}`:

    ```text
    You serve tenant {{tenant}}. Follow company safety policy.
    ```

    Placeholder names accept letters, digits, `.`, `-` and `_`.
  </Step>
  <Step title="Map each variable to a source">
    Every placeholder you type appears as a row under **Variables**. For each one, choose
    **Header** or **JWT claim** and give the name to read:

    | Placeholder | Source | Name |
    |---|---|---|
    | `tenant` | Header | `X-Tenant-Id` |

    The counter reads **1 of 1 resolved** once it is mapped. A placeholder with no source
    blocks the save — before this existed, it was saved happily and then rejected every
    request at runtime.

    <Warning>
      **JWT claim** reads the claim without verifying the token's signature. It is only
      trustworthy when the caller authenticates with that same bearer token. A consumer
      that authenticates with an API key or mTLS can send any `Authorization` header it
      likes, and the claim you read will be whatever it put there — so do not use a JWT
      claim for an authorization decision unless bearer auth is the only way in.
    </Warning>
  </Step>
  <Step title="Decide what happens when the value is missing">
    **If a variable is missing** covers the case where the header or claim is absent:

    | Option | Effect |
    |---|---|
    | **Skip this template** (default) | The template is not injected; the request continues. |
    | **Use empty string** | The placeholder becomes `""`. |
    | **Reject request** | The request fails with `400`. |

    The default is deliberate: the caller cannot fix a header it was never asked to send.
  </Step>
  <Step title="Choose how it combines, then save">
    **If system prompt exists** — **Merge** (default) appends to the caller's system
    prompt; **Replace** overwrites it. Then set mode (**Enforce** / **Observe**) and scope.
  </Step>
</Steps>

#### What the model receives

The caller sends this:

```json
{
  "model": "auto",
  "messages": [{ "role": "user", "content": "Reset my password" }]
}
```

With header `X-Tenant-Id: acme`, the model receives this:

```json
{
  "model": "auto",
  "messages": [
    { "role": "system", "content": "You serve tenant acme. Follow company safety policy." },
    { "role": "user", "content": "Reset my password" }
  ]
}
```

#### Equivalent API payload

```json
{
  "slug": "prompt_template",
  "settings": {
    "template_engine": "mustache",
    "context_variables": {
      "tenant": { "source": "header", "name": "X-Tenant-Id" }
    },
    "inject_templates": [
      {
        "id": "safety-policy",
        "position": "system",
        "role": "system",
        "content": "You serve tenant {{tenant}}. Follow company safety policy.",
        "on_existing_system": "merge"
      }
    ],
    "on_missing_context_variable": "skip_injection",
    "escape_json_control_chars": true
  }
}
```

`position` is fixed to `system` in v1. `context_variables` also accepts
`source: "jwt_claim"`, which reads a claim from the bearer token.

### Recipe: serve a versioned prompt library

Keep prompts on the gateway instead of in every client, and change them without shipping
a client release.

<Warning>
  Rendering a named template **replaces the entire `messages` array**. Any conversation
  history the client sent is discarded before the request reaches the model, so this fits
  single-turn calls. The trace reports how many turns were dropped as
  `discarded_messages`.
</Warning>

<Steps>
  <Step title="Create the policy">
    **TrustGate → Policies → Catalog → Prompt Template**, then pick **Publish a prompt
    library clients can invoke**.
  </Step>
  <Step title="Name the template">
    **Template name** is what clients put in the reference, so it is a public contract —
    `support-greeting` below.
  </Step>
  <Step title="Add a version with at least one label">
    Clients address a version **only by label**, so a version without one is unreachable
    and the console refuses to save it. Use labels you can repoint later, like `stable`
    and `latest`. Labels must be unique across every version of every template on the
    policy.

    Write the **Content** as a plain string, or as a JSON array of message objects when
    you need more than one turn.
  </Step>
  <Step title="Say where each placeholder comes from">
    Placeholders in a named template have two possible sources, and every one you write
    appears as a row under **Variables**:

    | Source | Who supplies it |
    |---|---|
    | **Sent by the client** (default) | The caller, under `properties` in the request. |
    | **Header** / **JWT claim** | The gateway, the same way auto-inject resolves them. |

    Leave a row as **Sent by the client** and the caller fills it; pick a header or a
    claim and the gateway does, so the caller cannot influence that value. Unlike
    auto-inject, an unmapped placeholder here is a valid template rather than an
    unfinished one.
  </Step>
  <Step title="Close the door on untemplated calls (optional)">
    **Require template reference** rejects any request that does not name a template. Turn
    it off to let normal traffic through the same policy.
  </Step>
  <Step title="Set a default label (optional), then save">
    **Default label** is used when a client omits the `@label` part. It must match a label
    that exists.
  </Step>
</Steps>

#### How a client calls it

In a **plain string** user message — not a multimodal content part:

```json
{
  "model": "auto",
  "properties": { "persona": "friendly" },
  "messages": [
    { "role": "user", "content": "{template://support-greeting@stable}" }
  ]
}
```

Drop the `@stable` to fall back to the policy's default label. Values under `properties`
fill the template's `{{placeholders}}`, alongside any context variables.

Resolution order: find the reference, resolve name → template, label (or default label) →
version, render placeholders, replace `messages`. Exactly one distinct reference per
request — repeating the same one is fine, since a multi-turn client resends it.

Per-version `required_variables` (type / enum / max_length) validate what clients send.
They have no editor yet; set them via the API and the console preserves them.

### Preview a configuration before you save it

**Preview** at the bottom of the panel runs the configuration currently on screen against
a request you paste, and shows the body the model would receive. Nothing is stored and no
traffic is sent.

Paste a sample body, add any headers the template reads — one `Name: value` per line —
and select **Run preview**. The result is one of three things: the rewritten request, a
note that the policy left it unchanged, or the rejection the caller would have received,
with the gateway's own status and message.

<Warning>
  Headers you paste are sent to the gateway as written. If a template reads a JWT claim,
  use a sample or expired token rather than a live one.
</Warning>

Preview is available for policies whose plugin opts into it. Prompt Template does; most
others do not, because running them for real would touch a rate-limit counter, a
provider or a collector.

### Troubleshooting

| The gateway answers | Usually means |
|---|---|
| `context variable "x" could not be resolved` | The header or claim is absent and **If a variable is missing** is set to **Reject request**. |
| `versions[0] must have at least one label` | A version was written via the API with no label. Add one. |
| `request does not reference a template` | **Require template reference** is on and the caller sent a plain message. |
| `template "x" not found` | The reference names a template this policy does not define. |
| `template "x" label could not be resolved` | The label does not exist and no default label is set. |
| `request references both a and b` | Two different references in one request. Only one template can be rendered. |
| `required variable "x" is missing` | The version declares `required_variables` and the caller omitted it from `properties`. |
| `mode not supported` on a preview | The preview was asked for a mode this policy cannot use. Prompt Template supports **Enforce** and **Observe**. |

### Field reference

**Add a system prompt to every request** (`inject_templates`)

| UI field | Backend | Meaning |
|---|---|---|
| **Identifier** | `inject_templates[].id` | Unique id, shown in traces (required). |
| **Content** | `content` | Template body with `{{var}}` placeholders (required). |
| **Variables** | `context_variables` | Maps each placeholder to a `header` or `jwt_claim` and its name. A `jwt_claim` is read unverified — see the warning above. |
| **If system prompt exists** | `on_existing_system` | **Merge** (default) or **Replace**. |
| **If a variable is missing** | `on_missing_context_variable` | `skip_injection` (default), `empty_string` or `error`. |

**Publish a prompt library** (`named_templates`)

| UI field | Backend | Meaning |
|---|---|---|
| **Template name** | `named_templates[].name` | Name in `{template://name…}` (unique, required). |
| **Labels** | `versions[].labels` | At least one, unique across all versions on the policy (required). |
| **Content** | `versions[].content` | Bare string or a JSON array of message objects (required). |
| **Require template reference** | inverted `allow_untemplated_requests` | Reject requests with no reference. |
| **Default label** | `default_label` | Used when a reference omits `@label`. Must match an existing label. |
| **Variables** | `context_variables` | Optional. Maps a placeholder to a `header` or `jwt_claim`; anything left unmapped comes from the caller's `properties`. |
| **If a variable is missing** | `on_missing_client_variable` | `error` (default) or `empty_string`. |

**Advanced**

| UI | Backend | Default | Meaning |
|---|---|---|---|
| **Sanitize substituted values** | `escape_json_control_chars` | on | Strip C0 control bytes from substituted values before insertion. |

## Prompt Compression

**`prompt_compression`** shrinks the request prompt on `pre_request` before the model runs.
Transforms are **deterministic** (same input → same bytes) so provider prompt-cache
prefixes stay stable, and the plugin **fails open**: any decode/transform error leaves the
original body unchanged.

The console uses the catalog **settings schema** form (booleans, integers, role multi-select).

### Configure in the console

1. **Policies** → **Catalog** → **Prompt Compression**.
2. Enable at least one transform (defaults are all on).
3. Tune thresholds and optional **target roles**.
4. Set mode and scope, then save.

### Settings

| Setting | Default | Meaning |
|---|---|---|
| **Compress JSON** (`compress_json`) | on | Minify standalone JSON message content, fenced JSON code blocks, and tool-call arguments (whitespace-only, lossless). |
| **Normalize Whitespace** (`normalize_whitespace`) | on | Trim trailing spaces per line (keeps Markdown two-space hard breaks) and collapse runs of blank lines. |
| **Strip ANSI Escapes** (`strip_ansi`) | on | Remove ANSI colour/cursor sequences (common in terminal/CI logs). |
| **Max Consecutive Blank Lines** | `1` | Longest blank-line run kept when whitespace is normalized (`1`–`1000`). |
| **Minimum Content Length** (`min_length`) | `256` | Skip message content shorter than this many bytes (protects tiny cache-stable prefixes). `0` = compress everything. |
| **Max Body Bytes** (`max_body_bytes`) | `1048576` (1 MiB) | Skip the whole pipeline for larger bodies (CPU bound). `0` = no cap. |
| **Target Roles** (`target_roles`) | empty = all | Restrict to `system` / `user` / `assistant` / `tool`. Empty compresses every role. |

At least one of compress JSON / normalize whitespace / strip ANSI must stay enabled.

### Example

```json
{
  "slug": "prompt_compression",
  "settings": {
    "compress_json": true,
    "normalize_whitespace": true,
    "strip_ansi": true,
    "max_consecutive_blank_lines": 1,
    "min_length": 256,
    "max_body_bytes": 1048576,
    "target_roles": ["user", "tool"]
  }
}
```
