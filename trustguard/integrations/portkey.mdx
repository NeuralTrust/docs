Portkey calls TrustGuard through a **Bring-Your-Own-Guardrails** webhook on requests and
responses.

## Coverage

| | Monitor | Block | Redact |
| --- | :--: | :--: | :--: |
| LLM input | ✅ | ✅ | ❌ |
| LLM output | ✅ | ✅ | ❌ |
| Tool-level | ➖ | ➖ | ➖ |

**Use it when** your apps already reach models through a Portkey Config and you
want one policy for all of them. **Not when** you need masking in flight: the
verdict contract is a boolean, so `transform` collapses to allow or deny — that
is [TrustGate](/trustguard/integrations/trustgate).

**Limits.** Without `deny: true` the guardrail is advisory: a failed check is
recorded and the request continues. Portkey mediates model traffic, so tool calls
around it are not seen.

Full comparison: [Coverage](/trustguard/integrations/coverage).

<Warning>
Portkey expects `{ verdict }`. Map TrustGuard `status` → `verdict` (e.g.
`verdict = status != "block"`) and apply `transformed_payload` on transform, or Portkey
will not enforce TrustGuard decisions.
</Warning>

1. Create an API key on the collector.
2. In Portkey, add a Guardrail **Webhook** check aimed at the evaluate URL.
3. Attach it under `input_guardrails` / `output_guardrails` with `deny: true`.
4. Map Portkey user / trace metadata to `consumer_id` and `session_id`.

```json
{
  "input_guardrails": [{
    "default.webhook": {
      "webhookURL": "{TRUSTGUARD_URL}/v1/evaluate",
      "headers": { "Authorization": "Bearer <collector-api-key>" }
    },
    "deny": true
  }]
}
```
