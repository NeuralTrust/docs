<p className="nt-lead">
  <code>POST /v1/evaluate</code> is the runtime endpoint for TrustGuard collectors.
  A <a href="/trustguard/concepts/collectors">collector</a> sends one request against
  its assigned <a href="/trustguard/concepts/policies">policy</a>.
  <a href="/trustguard/how-it-works">How it works</a> covers which actions each host can apply.
  The <strong>Inference Hooks</strong> collector uses the specialized endpoint in its
  <a href="/integrations/claude-enterprise">integration guide</a>.
</p>

## Base URL

Every path on this page is relative to your deployment's TrustGuard base URL, written
`{TRUSTGUARD_BASE_URL}` throughout these guides:

```http
POST {TRUSTGUARD_BASE_URL}/v1/evaluate
```

| Deployment | Base URL |
|---|---|
| **SaaS** | The public TrustGuard origin for your region, such as `https://trustguard.neuraltrust.ai`. |
| **Self-hosted / hybrid** | The TrustGuard data-plane endpoint your operator exposes. |

The authoritative value is in the console: open the collector and read the **Connection**
tab, which renders the setup snippet with your base URL already substituted.

<Warning>
Use the **public** TrustGuard origin, not an in-cluster service address. Self-hosted
deployments run TrustGuard behind an internal admin address that is not reachable from
gateways, SDKs, or edge workers, and is not the value to put in a collector snippet. If
the console shows a placeholder instead of a URL, it could not resolve a customer-facing
host — ask your operator for the data-plane endpoint rather than guessing.
</Warning>

**If you are the operator**, note that the deployment environment variable named
`TRUSTGUARD_URL` is the **internal admin** address, and is deliberately *not* what
`{TRUSTGUARD_BASE_URL}` means in these guides. The customer-facing origin comes from
`TRUSTGUARD_PUBLIC_URL` on SaaS, or from the guard data-plane endpoint you expose for a
hybrid deployment. Putting `TRUSTGUARD_URL` into a collector snippet is a common
misconfiguration — the request simply never arrives.

## Authentication

```http
POST /v1/evaluate
Authorization: Bearer <collector-api-key>
Content-Type: application/json
```

The collector is resolved from the API key, so you do not send a collector ID
in the body. (When TrustGuard runs behind [TrustGate](/trustgate/overview), the
gateway authenticates and calls this endpoint for you.)

| Field | Type | Required | Notes |
|---|---|---|---|
| `payload` | object | ✅ | The content to inspect. Accepts a minimal `{ "input": "…" }` (read as the user's message) or a full provider body (OpenAI, Anthropic, Gemini, MCP). On `direction: "output"`, send the model's completion as `{ "messages": [{ "role": "assistant", "content": "…" }] }`: Toxicity Detection and Custom Moderation read only `assistant` text on Output and skip a completion sent as `input`. `payload.attachments` is extracted separately (not sent to text detectors). Which fields of a provider body each detector reads is in [Where each detector applies](/trustguard/detectors/where-detectors-apply). |
| `direction` | enum | Optional | `input` (default) or `output`. Selects which [policy](/trustguard/concepts/policies) detector phase runs. [TrustGate](/integrations/trustgate) sets this value; other collectors must send it on every call, usually twice per turn. |
| `protocol` | enum | Optional | `all` (default), `llm`, `mcp`, or `a2a`. Available as the `protocol` gate or rule condition. |
| `session_id` | string | Optional | Conversation or correlation key. Synthesized if omitted. |
| `consumer_id` | string | Optional | Actor identifier for per-consumer policy routing. Gates match it as `consumer.id`. |
| `gateway_id` / `collector_key` | string | Conditional | Only for callers that authenticate with a service token: send exactly one to select the collector. Not needed with a collector API key. |
| `attributes` | object | Optional | Extra dimensions for gate and detector conditions: `consumer.{name,tag,type}`, `model.{name,provider}`, `collector.type`, `source.application`, and `tool.{name,command,arguments}`. `user.{id,email}` names the person behind the request; **Activity** shows it in the **User** column. Nested form: `{ "source": { "application": "claude-code-plugin" } }`. For MCP `tools/call`, `tool.name` is read first from **`payload.params.name`** (the last segment of `mcp__server__tool`). |

Unknown top‑level fields are rejected with `400` (strict decoding). Do **not**
send `input`, `metadata`, `collector_id`, or `detector_id` at the top level.

`direction` chooses which policy **Detectors** phase runs (`Input` vs `Output`).
If you only ever send `input` (or omit the field), Output-phase rules never
evaluate. Details and SDK examples:
[Python SDK](/sdks/trustguard/python).

Callers that authenticate with a **service token** instead of an API key must
also send exactly one of `gateway_id` or `collector_key` to select the
collector. With a collector **API key** (the common case, and the focus of this
page) the collector comes from the key.

### Attachments and SSRF

Each attachment in `payload.attachments` provides **either** base64 `data`
**or** a `url`:

- URL fetches use HTTPS and enforce timeout, size, and redirect limits.
- A strict **SSRF guard** resolves DNS before dialing and rejects loopback,
  private, link‑local, multicast, CGNAT (`100.64/10`), `0.0.0.0/8`, and
  cloud‑metadata (`169.254.169.254`) targets.
- Fetched URL content is not retained, and decoded attachment content is discarded
  once the detectors that consume it have run.

## Evaluation pipeline

```mermaid
flowchart TD
  REQ[POST /v1/evaluate] --> AUTH[1 · Authenticate<br/>resolve the collector from the API key]
  AUTH --> POL[2 · Resolve the policy<br/>per-consumer, else collector default]
  POL --> GATES[3 · Gates<br/>match request metadata]
  GATES -->|Block, Ask, or Skip<br/>detectors skipped| RED[5 · Reduce to one status]
  GATES -->|Report or no match| RULES[4 · Detector rules<br/>matching this direction]
  RULES --> DETECT[Detect phase<br/>concurrent, read-only]
  DETECT --> XFORM[Transform phase<br/>sequential, may rewrite]
  XFORM --> RED
  RED --> RESP[Response<br/>status + findings]
```

Each numbered step below is one box in that diagram.

### 1. Authenticate and resolve the collector

TrustGuard verifies the API key, checks that it is active and not expired, and
resolves its collector. A missing or invalid key returns `401`; an inactive or
expired key returns `403`. Authentication failures are rejected before any
evaluation runs.

### 2. Resolve the policy

TrustGuard uses the request's `consumer_id` to look for a per-consumer policy.
If none matches, it uses the collector's default policy.

If the collector has no matching policy, the request is unguarded: TrustGuard
returns `status: "allow"` with no findings. The policy's enforcement mode also
applies to this evaluation. In **Observe**, actions are recorded without
enforcement.

### 3. Run gates

[Gates](/trustguard/concepts/policies#gates) run before detectors, in saved
order (position, then `created_at`). Each gate matches request attributes, such
as consumer, model, collector, protocol, direction, tool, session, or source,
and takes an action:

| Gate action | Effect |
| --- | --- |
| **Block** | Stops evaluation. Detectors do not run. Returns `status: "block"`. |
| **Report** | Logs a finding and moves on. |
| **Skip** | Stops evaluation. Detectors do not run. Returns `status: "skip"` with a `gate_skip` finding. |
| **Ask** | Stops evaluation. Detectors do not run. Returns `status: "ask"`. Input only; an empty `direction` counts as input. Ignored on output. |

Disabled gates are ignored. The first matching Block, Skip, or Ask decides and
stops evaluation. Earlier Report findings are returned together with that
final Block, Skip, or Ask. Report logs and moves on. In report-only mode
(**Observe**), a downgraded Block or Ask is recorded as Report and continues
to later gates and the detectors. Skip still stops evaluation.

### 4. Run the detector rules

TrustGuard filters detector rules by the request's `direction` and each rule's
optional conditions. These are the same **Input** and **Output** phases
configured on the [policy](/trustguard/concepts/policies).

| Phase | Detectors | Execution |
| --- | --- | --- |
| **Detect** | Detection-only detectors | Run concurrently and merge results deterministically. They read the payload without modifying it. |
| **Transform** | Mutable detectors, currently `data_loss_prevention` | Run sequentially after detection. With the Transform action, they rewrite the payload and produce `transformed_payload`. |

Each rule's Monitor (`report`), Block, or Transform action sets `outcome.action`
on its findings. A Block rule also stops the remaining detector chain.

File attachments are decoded once and shared with detectors that consume them,
currently `doc_analyzer`. The `url_analyzer` detector finds URLs in the body or
messages, not in attachments. Remote attachment URLs are fetched server-side
under the [SSRF protections](#attachments-and-ssrf) described above.

### 5. Reduce to a status

TrustGuard reduces the findings to one top-level `status`, from most to least
restrictive:

```text
block → ask → transform → report → allow
```

A matching Skip gate returns `skip` instead of a ranked status. No detector
runs, and any earlier Report gate findings come back with it.

In **Observe**, Block, Ask, and Transform actions are downgraded, so the status
never exceeds `report`. The exception is a Skip gate, which still returns `skip`.

## Response

A successful evaluation returns `200`, including one whose status is `block`.

```json
{
  "status": "transform",
  "transformed_payload": { "input": "My email is [MASKED_EMAIL]" },
  "findings": [
    {
      "source": {
        "kind": "detector",
        "plugin": "data_loss_prevention",
        "detector_id": "…",
        "detector_name": "PII masking",
        "policy_id": "…"
      },
      "signal": { "type": "pii", "confidence": 1.0 },
      "outcome": { "action": "transform" },
      "evidence": { "masked": 1, "entities": ["email"] }
    }
  ],
  "trace_id": "f1e2…",
  "request_id": "a9b8…"
}
```

| Field | Type | Notes |
|---|---|---|
| `status` | enum | The reduced verdict: `allow`, `report`, `transform`, `ask`, `block`, or `skip`. The most restrictive status wins (`block` > `ask` > `transform` > `report` > `allow`). `skip` is returned only when a Skip gate matches. Detectors don't run, so it never competes with a detector status, and it takes precedence over any earlier Report gate findings returned with it. |
| `transformed_payload` | object \| null | The rewritten payload; `null`/absent unless a Transform rule (mutable detector) changed it. |
| `findings[]` | array | One entry per gate or detector that fired. |
| `trace_id` / `request_id` | string | Correlation IDs (also on logs and telemetry). |

### The finding object

| Field | Type | Notes |
|---|---|---|
| `source.kind` | enum | `gate` or `detector`. |
| `source.gate_name` | string | Gate findings only. |
| `source.gate_id` | string (UUID) | Gate findings only. Stable UUID of the gate (`Gate.ID`); survives rename so audits can still tie older events to the same gate. Omitted (`omitempty`) when empty or a zero UUID — never emit a fake id. |
| `source.plugin` | string | The catalog detector slug for detector findings, such as `prompt_guard`. |
| `source.detector_id` / `source.detector_name` | string | The detector instance that fired. |
| `source.policy_id` | string | The policy that produced the finding. |
| `signal.type` | string | What was detected, such as `jailbreak`, `pii`, `secret`, `nt_topic` (Custom Moderation), a toxicity category, an Indirect Prompt Injection category (or `indirect_prompt_injection`), `ssrf_probe`, `url_domain_blocked`, `url_analysis_incomplete` (URL Analyzer, when some links were not analysed), `excessive_json_nesting` (Prompt Guard, Toxicity or Custom Moderation, when the input nests JSON inside strings too deeply to score, which could hide text from the detector), `purview_dlp_block` (Microsoft Purview DLP, when a Purview policy restricts the content), `purview_identity_missing` (Microsoft Purview DLP, when the request has no end user identity and the detector is set to block that), `purview_unavailable` (Microsoft Purview DLP, when Purview does not answer and the detector is set to fail closed), or `gate_block`, `gate_report`, `gate_ask`, or `gate_skip`. A detector that did not run reports one of the signals in [Failure behavior](#failure-behavior). |
| `signal.confidence` | number | Detector‑specific score in `[0, 1]` (optional). |
| `outcome.action` | enum | The action applied by the rule: `report`, `transform`, `ask`, `skip`, or `block`. Optional on observational runs. |
| `not_executed` | boolean | `true` when the finding stands for a detector that was configured but did not run. Omitted otherwise. |
| `evidence` | object | Free‑form, detector‑specific context (e.g. matched entities, masked count, matched rule). A finding for a detector that did not run carries `reason`, and a `guard_failed_closed` finding also carries `failure_mode: "closed"`. A URL Analyzer finding always includes `urls_total`, `urls_analyzed`, `urls_unanalyzed`, and `url_analysis_incomplete`. See [URL Analyzer](/trustguard/detectors/content-security#links-it-could-not-analyse). |

## Status codes

| Code | When |
|---|---|
| `200` | Successful evaluation, **including a `block` status**. The caller enforces. |
| `400` | Invalid body, unknown fields, bad `direction`/`protocol`, or a bad collector reference. |
| `401` | Missing or invalid API key. |
| `402` | The organization's usage is exhausted. The body carries a `reason`. |
| `403` | Key found but inactive/expired. |
| `429` | Plan burst or monthly quota exceeded. The body carries a `reason`. See [Limits and quotas](#limits-and-quotas). |
| `500` | An internal error. A detector that cannot run is not a `500`: see [Failure behavior](#failure-behavior). |
| `503` | Rate-limit entitlements could not be loaded, or the usage state could not be resolved, so TrustGuard would not evaluate blind. Retry later. |

Error responses carry `{ "error", "trace_id", "request_id" }`.

## Limits and quotas

| Limit | Value |
|---|---|
| Request body | **10 MiB** by default, set per deployment. A larger body is rejected before evaluation. |
| Persisted body, for findings evidence | **1 MiB** after credential redaction; longer bodies are stored truncated. See [Data handling](/trustguard/data-handling). |
| Rate limit | A **burst** limit plus a **monthly quota**, both from your plan entitlements. |
| `url_analyzer` fetch timeout | **20 s** by default, configurable on the detector. |

### Rate limiting

Exceeding either limit returns `429` with standard headers, so a client can back off
without parsing the body:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reason: burst
```

Honour `Retry-After` rather than retrying immediately. `X-RateLimit-Reason` distinguishes
a short burst from an exhausted monthly quota — the first clears on its own, the second
needs a plan change. Your plan's numbers are in the console; they are not fixed across
plans, so treat the headers as the source of truth at runtime.

Per-request latency depends on which detectors a policy runs and on your deployment.
There are no published latency figures yet — measure against your own policy before you
set a client timeout, and see [Failure behavior](#failure-behavior) for what happens when
TrustGuard is slow or unavailable.

### Failure behavior

When a detector cannot run, such as after an upstream outage, a timeout, or a
misconfigured detector, TrustGuard does not skip it and carry on. A direct
integration always fails closed, and there is no setting to change that. Calls
made through the gateway are different: the TrustGuard policy there has its own
[**If the guardrail cannot evaluate**](/trustgate/policies/trustguard-guardrail#if-the-guardrail-cannot-evaluate)
field.

The response is still HTTP `200`. The detector appears as a finding:

```json
{
  "status": "block",
  "findings": [
    {
      "source": { "kind": "detector", "plugin": "prompt_guard", "detector_name": "…" },
      "signal": { "type": "guard_failed_closed" },
      "outcome": { "action": "block" },
      "not_executed": true,
      "evidence": { "reason": "execution_failed", "failure_mode": "closed" }
    }
  ]
}
```

A detector set to report only reports. Any other detector blocks, a Transform
one included: it masked nothing, so the request is not let through unmasked.

| `signal.type` | Meaning | `evidence.reason` |
|---|---|---|
| `guard_failed_closed` | The detector could not run: an outage, a timeout, or a bad configuration. | `execution_failed`, `plugin_panic`, `unknown_plugin`, `invalid_plugin_config`, `missing_dependency` |
| `guard_payload_too_large` | The payload was over the detector's size limit. | `payload_too_large` |
| `guard_content_uninspectable` | The detector could not read an attachment. | `content_uninspectable` |
| `guard_payload_ambiguous` | The body mixed MCP (JSON-RPC) and chat fields and was refused unread. | `ambiguous_payload` |

`guard_payload_ambiguous` follows the same rule. `guard_payload_too_large` and
`guard_content_uninspectable` take the action of the detector's rule as it is.
Only `guard_failed_closed` carries `failure_mode`.

These are not detections. In **Activity** the request shows the detector as not
executed and the action that was applied. A structured Block decision from a
gate or detector rule applies as before.

## Enforcing the verdict

TrustGuard is advisory. Your collector inspects the `status` and decides:

```text
status == "block"                    → block / 4xx the original request
status == "ask"                      → IDE permission prompt (input only)
status == "transform"                → forward transformed_payload instead
status == "report"                   → forward unchanged, record the finding
status == "allow"                    → forward unchanged
status == "skip"                     → forward unchanged; a gate skipped the detectors, so the content was not inspected
```

When TrustGuard runs behind [TrustGate](/trustgate/overview), the gateway
performs this enforcement for you.
