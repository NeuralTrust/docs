description: "TrustGuard inspects LLM and agent traffic against a policy and returns a verdict — allow, report, transform, ask, or block — that the collector enforces."

**TrustGuard** is NeuralTrust's runtime security engine. It inspects prompts, completions,
documents, URLs, and tool calls, then returns a structured verdict. It is **not** a
gateway: it does not route, load-balance, or talk to model providers. The
[collector](/trustguard/concepts/collectors) that called it decides whether to allow,
mask, prompt the user, or block.

It sits next to **[TrustGate](/trustgate/overview)** (native inline enforcement) and
**[TrustTest](/trusttest/getting-started/overview)** (red teaming). You can also attach it
to another gateway, an SDK, a browser/WAF worker, or a coding-agent plugin.

## What it inspects

| Area | Catalog |
|---|---|
| Jailbreaks, toxicity, topic/keyword moderation | [Content security](/trustguard/detectors/content-security) |
| PII and secrets (optional in-flight masking) | [Data loss prevention](/trustguard/detectors/data-loss-prevention) |
| URLs and uploaded documents (indirect prompt injection, PII) | `url_analyzer`, `doc_analyzer` |
| Tool-sourced content (MCP / `role=tool`) | [Agent & MCP security](/trustguard/detectors/agent-mcp-security) |

Detectors only **find**. What happens next is the [policy](/trustguard/concepts/policies):
gates first (match attributes — consumer, model, tool, source, …), then detector rules
(**Monitor** / **Block** / **Transform**).

## Where traffic comes from

Create a collector under **Runtime → Collectors → Catalog**.

| Group | Examples |
|---|---|
| **Gateway** | [TrustGate](/trustguard/integrations/gateway/trustgate) (native — no `tgk_…` key), Portkey, LiteLLM, Kong, Apigee, Azure APIM |
| **AI assistants & coding agents** | [Claude Enterprise](/trustguard/integrations/ide/claude-enterprise), [Claude Code](/trustguard/integrations/ide/claude-code), [Cursor](/trustguard/integrations/ide/cursor), [Codex](/trustguard/integrations/ide/codex), [GitHub Copilot](/trustguard/integrations/ide/copilot) |
| **Application** | [Python](/trustguard/integrations/application/python-sdk) / [Node](/trustguard/integrations/application/node-sdk) SDK, REST, middleware |
| **Browser / WAF** | Chrome, Edge, Firefox; Cloudflare, CloudFront, Fastly, Akamai |

Most collectors call [`POST /v1/evaluate`](/trustguard/api/evaluate) with a collector
API key. TrustGate authenticates as the gateway. Claude Enterprise uses
`POST /v1/evaluate/claude`.

<Warning>
A collector with **no matching policy** is **unguarded**: TrustGuard returns
`status: "allow"` and inspects nothing. Assign a default policy (and per-consumer
overrides if you need them) before you rely on it.
</Warning>

## AI assistants & coding agents

The **AI assistants & coding agents** catalog group covers AI assistants and developer
tools. TrustGuard sees **prompts and tool use** (shell, MCP `tools/call`, tool
results), not only chat.

| Collector | Path | `source.application` | Enforcement |
|---|---|---|---|
| [Claude Enterprise](/trustguard/integrations/ide/claude-enterprise) | Org Inference Hooks (`/v1/evaluate/claude`) | `claude-ai`, `claude-code` | Allow or deny. **Ask** is not a dialog here. |
| [Claude Code](/trustguard/integrations/ide/claude-code) | Laptop plugin + binary + `tgk_…` | `claude-code-plugin` | Block / Ask on input (prompt, PreToolUse) |
| [Cursor](/trustguard/integrations/ide/cursor) | Plugin + MDM `cursor.json` | `cursor-plugin` | Same; Ask is Cursor’s permission dialog |
| [Codex](/trustguard/integrations/ide/codex) | Plugin / managed hooks + `codex.json` | `codex-plugin` | Block to stop. Ask is extra context only (no dialog) |
| [GitHub Copilot](/trustguard/integrations/ide/copilot) | Plugin / policy hooks + `copilot.json` | `copilot-plugin` | Deny / Ask on tool use; prompt event is audit-only |

A gate on `claude-code` (Inference Hooks) does **not** match the laptop plugin
(`claude-code-plugin`). TrustGate MCP is an [org Connector](/trustgate/mcp/claude), not
these plugins — do not put a `tgk_…` key on the connector.

Full list: [Integrations](/trustguard/integrations/overview).

## Building blocks

| Concept | What it is |
|---|---|
| **[Detector](/trustguard/concepts/detectors)** | A named instance of a [catalog](/trustguard/detectors/overview) detector plus its settings. Detection-only. |
| **[Policy](/trustguard/concepts/policies)** | Gates + detector rules (Input / Output), and **Observe / Enforce**. Built under **Runtime → Policies**. |
| **[Collector](/trustguard/concepts/collectors)** | One tap. Routes each request to a policy. |
| **Finding** | What a gate or detector reported (`source`, `signal`, `outcome`, `evidence`). |

The request does **not** name detectors. TrustGuard resolves the collector, picks the
policy, runs gates, then the detector rules that match `direction`. See
[How it works](/trustguard/how-it-works).

## Observe vs Enforce

On the policy **Basics** tab:

| Console | Effect |
|---|---|
| **Observe** | Record only. Status never goes past `report`. |
| **Enforce** | Apply **Block** / **Ask** / **Transform** as configured. |

```text
block  →  ask  →  transform  →  report  →  allow
```

The collector acts on `status`. TrustGate does it on the route; IDE plugins deny the
tool or show a permission prompt. A detection is `HTTP 200` even when `status` is
`block` — non-2xx is auth, a bad body, or a fail-closed detector error.

## Get started

1. Create a [collector](/trustguard/concepts/collectors) — TrustGate, a coding-agent
   collector, or an SDK.
2. Create [detectors](/trustguard/detectors/overview) you need (skip this if the policy
   is gates only).
3. Create a [policy](/trustguard/concepts/policies) in **Observe**. Add gates and/or
   Input / Output detector rules.
4. Attach it to the collector (**Policies** tab on the collector, or **Collectors** on
   the policy).
5. Run a sample on the policy **Test** tab, then check **Activity**.
6. Switch the policy to **Enforce** when the signal looks right.
