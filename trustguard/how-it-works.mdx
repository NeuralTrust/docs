[TrustGuard](/trustguard/overview) evaluates content against a policy and returns
a verdict. Each [collector](/trustguard/concepts/collectors) applies that verdict
using the capabilities of its host platform. [TrustGate](/trustgate/overview)
appears here through its native collector, which evaluates traffic routed through
the gateway.

The tables below describe TrustGuard coverage, not the full capabilities of
each host platform. For request processing and response fields, see the
[Evaluate API](/trustguard/api/evaluate#evaluation-pipeline).

## Policy actions

One request can trip several rules. TrustGuard reduces them to a single outcome
and hands the host that one answer, worst first:
**Block** → **Ask** → **Transform** → **Monitor** → **Allow**.

| Outcome | What the host is asked to do |
| --- | --- |
| **Block** | Stop the interaction wherever it enforces. |
| **Ask** | Get a human to confirm, where the host has somewhere to ask. Input only. |
| **Transform** | Forward the masked version instead of the original. Only [Data Loss Prevention](/trustguard/detectors/data-loss-prevention) produces this. |
| **Monitor** | Record the finding and carry on. |
| **Allow** | Nothing needed action. |

Redaction requires the host to own and modify the payload. Integrations that
return only a yes-or-no verdict cannot mask anything.

**Ask** applies only to input. Interactive development tools may show an
approval prompt; noninteractive integrations must map the status to allow or
block:

| Collector | What **Ask** does there |
| --- | --- |
| [Claude Code](/integrations/claude-code) | **Supported on tool calls** through the native permission dialog. On prompt events, the prompt is submitted with a warning because no dialog is available. |
| [Cursor](/integrations/cursor) | **Supported on tool calls** through Cursor's approval prompt. On prompt events, the prompt is submitted with a warning because no dialog is available. |
| [GitHub Copilot](/integrations/github-copilot) | **Supported on tool calls** through Copilot's approval prompt. In Copilot cloud jobs, where nobody is there to answer, Ask is treated as a denial. |
| [Codex](/integrations/codex) | **Allowed**, with a warning added to the agent context. On tool-result events, Ask is discarded without a decision or added context. |
| [n8n](/integrations/n8n#5-wire-the-four-outputs) | **Routed to Block.** The outcome stays Ask, so a workflow can branch to an explicit approval step. Workflow connections determine whether execution continues. Since version 0.2.0, the node no longer fails on this status. |
| [LangChain](/integrations/langchain) | **Blocked** — the middleware has no Ask case and fails closed on anything it does not recognise. |
| [Inference Hooks](/integrations/claude-enterprise) | **Allowed** because this integration returns only allow or deny and has no interactive prompt. |
| [TrustGate](/integrations/trustgate) | **Blocked in Enforce** because the gateway has no interactive approval flow. In Observe, the verdict is recorded and traffic continues. |
| [LiteLLM](/integrations/litellm) | **Blocked.** The proxy has no approval flow, so `ask` is treated as `block`. |
| Other gateways | **Allowed**, and recorded. There is nobody to prompt and the outcome is not Block, so the request passes through. |
| Application collectors | **Whatever you build.** The outcome is advisory; your code has to implement the approval flow. |

Collectors cover different traffic paths. A gateway collector covers your AI
services, while a coding-agent collector covers developer and agent activity on
local machines. Neither sees the other's traffic.

**Streaming responses:** TrustGate buffers the stream and inspects after the
client drain, so streamed output findings are monitor-only there.
[LiteLLM](/integrations/litellm) scans accumulated output **during** the
stream: `block` stops later chunks, and `transform` reaches streamed tokens
when `streaming_transform_mode: incremental_diff` is set. Tokens already sent
cannot be pulled back. The other gateway integrations cover only non-streaming
responses.

**Azure APIM output:** It can mask on the way in, but not on the way back —
covering responses at all requires adding the outbound policy.

**Copilot prompts:** Copilot ignores what the hook returns on a submitted
prompt, so prompts are recorded but cannot be stopped at that point.
Enforcement happens at the tool events.

**Copilot Studio prompts:** Microsoft hosts inference and exposes no hook for
it, so the model response is never seen and the model in use is never sent — a
rule targeting a specific model cannot be written on this path at all. The
user's message *is* evaluated, but only at the moment a tool is about to run, so
a conversation that never calls a tool is never inspected. Write every rule for
this collector in the **Input** direction; an Output rule saves but is never
reached.

Tool-result hooks run after the tool call and cannot undo it. Claude Code and
Codex can return a block decision and reason as post-tool feedback, but they do
not replace the result content. Cursor adds the finding as an untrusted-content
warning and does not return a permission decision. GitHub Copilot support is
conditional because result replacement works only with its native payload.

Middleware collectors see HTTP routes rather than model or tool calls, so they do
not expose tool-level coverage. SDK integrations can send tool events explicitly.

Catching a poisoned **tool description** needs an integration that reports which
tools the agent was offered, not just which one it called. That rules out the
developer-machine plugins: they send tool calls and results, but never the list.
It is available from [TrustGate](/trustgate/mcp/overview) on MCP, from
[LangChain](/integrations/langchain) for bound tools, and from the
[Inference Hooks](/integrations/claude-enterprise) transcript — where the only
available response is to deny the whole inference.

## Choose an integration

| If you need | Use |
| --- | --- |
| Masking sensitive data in flight | [TrustGate](/integrations/trustgate) for non-streaming LLM responses and MCP traffic. [LiteLLM](/integrations/litellm) for LLM traffic, including streamed redaction when `streaming_transform_mode: incremental_diff` is set |
| Coverage of streaming completions | [TrustGate](/integrations/trustgate) if the client must see no tokens until inspection finishes. [LiteLLM](/integrations/litellm) if scanning during the stream is enough |
| A developer confirmation dialog | [Claude Code](/integrations/claude-code), [Cursor](/integrations/cursor), or [GitHub Copilot](/integrations/github-copilot). These integrations support **Ask** on tool calls |
| Inspection of tool declarations for tool poisoning | [TrustGate](/trustgate/mcp/overview) on MCP, or [LangChain](/integrations/langchain) inside the agent |
| Enforcement as a visible step in a low-code workflow | [n8n](/integrations/n8n), where the verdict becomes a branch on the canvas |
| Organization-wide Claude coverage with nothing installed | [Inference Hooks](/integrations/claude-enterprise) |
| Stopping a specific shell command or MCP call | [Claude Code](/integrations/claude-code), [Cursor](/integrations/cursor), [Codex](/integrations/codex), [Copilot](/integrations/github-copilot) |
| A policy decision that needs application context | An [SDK](/sdks/trustguard/python) or [REST](/integrations/rest) integration |
| Coverage without touching application code | A [gateway](/integrations/trustgate) collector |

Every integration page states what that host can actually enforce, in the
capability row at the top — **Monitor**, **Block**, and whether redaction is
supported at all. Read that row before committing to an integration: a host that
lists only Monitor and Block cannot mask, whatever the policy says.

Create the policy in **Observe** mode. Observe records decisions in **Activity**
without enforcing them. Review the results, then switch the policy to **Enforce**.
