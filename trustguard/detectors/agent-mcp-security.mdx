Agent and MCP security detectors protect tool-using agents from **indirect prompt
injection** — hostile instructions that arrive in what a tool hands back, rather
than in what the user typed.

| Console card | Sides | Protocols | Configuration tab shows |
|---|---|---|---|
| **Indirect Prompt Injection** | Input, Output | LLM, MCP | Protection Sensitivity |

## Indirect Prompt Injection

### What it protects against

An instruction the user never typed. It arrives inside data the agent reads — a
ticket, a record, an email, an API response — and redirects what the agent does
next. The tool call that follows looks entirely normal, which is why no other
detector catches this: the evidence is in what came back, not in what is about
to be sent.

It also reads the tool and function descriptions offered to the model, which is
where **tool poisoning** hides — a malicious instruction written into a tool's
own description rather than into its output.

### What it does not read

Only tool-sourced content is scored. Messages from the user, the assistant, or the
system are skipped, so a turn with no tool activity produces no findings at all.
There is no fallback to the rest of the conversation.

That is deliberate, and it is the reason this detector pairs with
**Prompt Guard** rather than replacing it: one watches what comes back from tools,
the other watches what the person types.

### Configure

1. Open **Detectors** → **New detector** → **Indirect Prompt Injection**.
2. On **Basics**, give it a **Name**.
3. On **Configuration**, pick a
   [**Protection Sensitivity**](/trustguard/detectors/content-security#protection-sensitivity)
   preset — **Permissive**, **Balanced**, or **Strict**. That is the only setting.
4. **Create detector**, then reference it from a
   [policy](/trustguard/concepts/policies) rule.

## When to use

- Any agent that calls tools or MCP servers and feeds the results back into the
  model context.
- Pair it with [Prompt Guard](/trustguard/detectors/content-security#prompt-guard)
  for direct jailbreaks in user prompts. Neither one covers the other's ground.
- Start with the policy in **Observe**. Tool-heavy agents can surface a lot of
  findings on day one, and you want to see them before they block anything.
