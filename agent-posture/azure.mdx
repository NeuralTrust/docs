Agent Posture supports two types of Azure AI agents under a single integration:

- **Azure AI Foundry Agents (v2)** — agents built with the Azure AI Foundry Agents SDK, hosted in AI Services accounts
- **Azure OpenAI Classic Assistants (v1)** — assistants built with the Azure OpenAI Assistants API

A single integration discovers both types automatically from your subscription.

---

## What Agent Posture discovers

### Azure AI Foundry agents (v2)

| Data | Source |
|------|--------|
| Agent name, description, status | Azure AI Foundry Agents API |
| Model, instructions, tools | Azure AI Foundry Agents API |
| Knowledge bases (vector stores) | Azure AI Foundry Agents API |
| Content filters / RAI policies | Cognitive Services Management API |
| Guardrails configuration | Derived from RAI policies |
| Usage metrics (runs, tokens, latency, errors, tool calls) | Application Insights via Log Analytics (requires telemetry setup — see below) |

### Azure OpenAI Classic assistants (v1)

| Data | Source |
|------|--------|
| Assistant name, description, status | Azure OpenAI Assistants API |
| Model, instructions, tools | Azure OpenAI Assistants API |
| Vector stores (knowledge bases) | Azure OpenAI Assistants API |
| Usage metrics (runs, conversations, tool call counts) | Assistants API — Threads & Run Steps (no Log Analytics required) |

<Note>
Content filters and guardrails are not exposed via the Azure OpenAI Assistants (v1) API. These fields will show as unavailable for Classic assistants.
</Note>

## Required permissions

### Simple setup — one role (recommended)

Assign **Azure AI User** to the service principal at the **subscription level**:

| Role | Scope | Purpose |
|------|-------|---------|
| `Azure AI User` | Subscription | Discover Cognitive Services accounts and projects (management plane), list agents, models, datasets, and vector stores (data plane), read RAI policies and content filters |

**Why this role:** Azure AI User includes both `Microsoft.CognitiveServices/*/read` (management plane — enumerate accounts, read RAI policies, read diagnostic settings) and `Microsoft.CognitiveServices/*` (data plane — access agents, models, datasets). Assigning it at subscription level means it applies to all AI Services resources in the subscription automatically.

<Warning>
**Azure AI Developer** is a different role focused on ML Workspaces. It does **not** include `Microsoft.CognitiveServices/*/read` and cannot discover Cognitive Services accounts. Do not use it for this integration.
</Warning>

### Granular setup — two roles (least-privilege alternative)

If your security policy requires strictly minimal permissions, you can use two more targeted roles instead:

| Role | Scope | Purpose |
|------|-------|---------|
| `Reader` | Subscription | Enumerate Cognitive Services accounts, read account metadata, read RAI policies, read diagnostic settings |
| `Cognitive Services OpenAI User` | Each AI Services / OpenAI resource | Access the data plane to list agents, models, assistants, vector stores |

<Note>
With the granular approach, you must assign `Cognitive Services OpenAI User` on **each** AI Services resource individually. Using Azure AI User at subscription level is simpler and equally secure for read-only access.
</Note>

### Optional — telemetry (usage metrics, v2 only)

For **Azure AI Foundry (v2)** agents, Agent Posture collects usage metrics, token counts, latency, error rates, and tool call breakdowns (code interpreter, file search, function calls) from **Application Insights** via a linked Log Analytics workspace. This requires:

| Role | Scope | Purpose |
|------|-------|---------|
| `Log Analytics Reader` | Log Analytics Workspace | Query Application Insights traces (AppDependencies table) |

**What you lose without this:** v2 usage statistics and tool call metrics will be unavailable. v1 Classic usage is collected directly via the Assistants API and does **not** require this role.

**What you gain:** Per-agent usage metrics, conversation-level telemetry signals (used for aggregation, not enumeration), per-tool call breakdown by type (code interpreter, file search, custom functions), token consumption, and latency.

## Prerequisites

Before configuring the integration, ensure you have:

- An Azure subscription containing AI Services or Azure OpenAI resources
- Permission to create app registrations and assign RBAC roles (User Access Administrator or Owner on the subscription)
- For v2 telemetry: an **Application Insights** resource connected to your AI Foundry project, linked to a Log Analytics workspace (see [Enabling telemetry](#enabling-telemetry))

## Step-by-step setup

<Steps>
  <Step title="Create a service principal">
    <Tabs>
      <Tab title="Azure CLI">
        ```bash
        az ad sp create-for-rbac --name "neuraltrust-agent-posture" --skip-assignment
        ```
        Save the output — you will need `appId` (client ID), `password` (client secret), and `tenant` (tenant ID).
      </Tab>
      <Tab title="Azure Portal">
        1. Go to **Microsoft Entra ID** → **App registrations** → **New registration**
        2. Name the app (e.g., `neuraltrust-agent-posture`)
        3. Select **Single tenant**
        4. Click **Register**
        5. Go to **Certificates & secrets** → **New client secret**, set an expiry, and copy the secret value immediately
      </Tab>
    </Tabs>
  </Step>

  <Step title="Assign the Azure AI User role">
    <Tabs>
      <Tab title="Azure CLI">
        ```bash
        SUBSCRIPTION_ID=$(az account show --query id -o tsv)
        APP_ID="<your-app-id>"

        az role assignment create \
          --assignee $APP_ID \
          --role "Azure AI User" \
          --scope /subscriptions/$SUBSCRIPTION_ID
        ```
      </Tab>
      <Tab title="Azure Portal">
        1. Go to **Subscriptions** → select your subscription → **Access control (IAM)**
        2. Click **+ Add** → **Add role assignment**
        3. Search for and select **Azure AI User**
        4. Assign it to your service principal
        5. Click **Save**
      </Tab>
    </Tabs>
  </Step>

  <Step title="(Optional) Assign Log Analytics Reader for telemetry">
    Skip this step if you do not need v2 usage metrics.

    <Tabs>
      <Tab title="Azure CLI">
        ```bash
        WORKSPACE_ID=$(az monitor log-analytics workspace show \
          --resource-group <resource-group> \
          --workspace-name <workspace-name> \
          --query id -o tsv)

        az role assignment create \
          --assignee $APP_ID \
          --role "Log Analytics Reader" \
          --scope $WORKSPACE_ID
        ```
      </Tab>
      <Tab title="Azure Portal">
        1. Go to the **Log Analytics workspace** → **Access control (IAM)**
        2. Click **+ Add role assignment** → select **Log Analytics Reader**
        3. Assign to your service principal → click **Save**
      </Tab>
    </Tabs>
  </Step>

  <Step title="Configure the integration in Agent Posture">
    Provide the following credentials when creating the Azure integration:

    | Field | Where to find it |
    |-------|-----------------|
    | **Tenant ID** | Azure Portal → Microsoft Entra ID → Overview → Directory (tenant) ID |
    | **Client ID** | Azure Portal → App registrations → your app → Application (client) ID |
    | **Client Secret** | Copied in Step 1 |
    | **Subscription ID** | Azure Portal → Subscriptions → your subscription → Subscription ID |
  </Step>
</Steps>

## Enabling telemetry

Agent Posture retrieves v2 usage metrics from **Application Insights** via a linked Log Analytics workspace. Azure AI Foundry automatically writes server-side OpenTelemetry traces (`gen_ai.*` semantic conventions) to the `AppDependencies` table when a Foundry project is connected to Application Insights. Agent Posture queries this table to produce per-agent usage, token counts, latency, and tool call breakdowns.

<Note>
**Classic (v1) assistants do not require this setup.** Usage for v1 assistants is collected directly from the Assistants API (Threads and Run Steps) and is always available once the core RBAC role is in place.
</Note>

<Steps>
  <Step title="Connect Application Insights to your AI Foundry project">
    <Tabs>
      <Tab title="AI Foundry Portal">
        1. Open [Azure AI Foundry](https://ai.azure.com) and navigate to your project
        2. Go to **Settings** → **Tracing**
        3. Select or create an **Application Insights** resource
        4. Save — Azure will begin writing traces automatically; no SDK instrumentation is required
      </Tab>
      <Tab title="Azure CLI">
        ```bash
        az ml workspace update \
          --name <foundry-project-name> \
          --resource-group <resource-group> \
          --application-insights /subscriptions/<subscription-id>/resourceGroups/<resource-group>/providers/microsoft.insights/components/<appinsights-name>
        ```
      </Tab>
    </Tabs>
  </Step>

  <Step title="Grant Log Analytics Reader on the linked workspace">
    Application Insights stores trace data in a linked Log Analytics workspace. Find the workspace and grant access:

    <Tabs>
      <Tab title="Azure CLI">
        ```bash
        WORKSPACE_ID=$(az monitor log-analytics workspace show \
          --resource-group <resource-group> \
          --workspace-name <workspace-name> \
          --query id -o tsv)

        az role assignment create \
          --assignee $APP_ID \
          --role "Log Analytics Reader" \
          --scope $WORKSPACE_ID
        ```
      </Tab>
      <Tab title="Azure Portal">
        1. Go to the **Log Analytics workspace** → **Access control (IAM)**
        2. Click **+ Add role assignment** → select **Log Analytics Reader**
        3. Assign to your service principal → click **Save**

        The workspace is found in the Application Insights resource under **Settings** → **Linked workspace**.
      </Tab>
    </Tabs>

    <Note>
    Traces may take a few minutes to appear after the first agent invocations.
    </Note>
  </Step>
</Steps>

### Telemetry source summary

| Data type | Source | Requires |
|-----------|--------|----------|
| v2 usage metrics (runs, tokens, latency, errors) | Application Insights — AppDependencies | App Insights connected to Foundry project + Log Analytics Reader |
| v2 tool call breakdown (code interpreter, file search, functions) | Application Insights — AppDependencies | Same as above |
| v1 usage metrics (runs, conversations, tool call counts) | Assistants API (Threads + Run Steps) | Core RBAC role only — no Log Analytics needed |

## Known limitations

| Limitation | Details |
|------------|---------|
| No conversation enumeration for v2 | The Azure AI Foundry API does not expose a `conversations.list()` endpoint. App Insights provides conversation-level telemetry signals (conversation ID, message count, latency per conversation) used for aggregation — not a list of conversations you can browse. |
| Tool call telemetry requires App Insights (v2) | Tool call breakdown (code interpreter, file search, function calls) requires Application Insights connected to the Foundry project. Foundry automatically emits `gen_ai.tool.name` spans — no client instrumentation needed. |
| Content filters unavailable for v1 | The Azure OpenAI Assistants (v1) API does not expose content filter or RAI policy configuration. These fields show as unavailable for Classic assistants. |
| App Insights trace delay | Traces may take a few minutes to appear in Log Analytics after initial agent invocations. |
| Conversation ID mismatch (v2) | Application Insights `conversation_id` values (UUID format) do not match Foundry API conversation IDs (`conv_xxx` format). Agent Posture uses telemetry-level aggregation. |

---

## Security considerations

- The service principal has **read-only** access. Agent Posture cannot modify, delete, or create any Azure resources.
- `Azure AI User` at subscription level includes `listkeys/action` (the ability to read API keys for Cognitive Services accounts). If your policy prohibits this, use the granular setup (Reader + Cognitive Services OpenAI User), which does not include key listing.
- Client secrets should be rotated regularly. Update the integration in Agent Posture when you rotate the secret.
- All credentials are encrypted at rest.

## Troubleshooting

<AccordionGroup>
  <Accordion title="No agents found in my subscription">
    - Verify the service principal has **Azure AI User** at the subscription level (not at a resource group or resource level only).
    - Confirm your AI agents are deployed in AI Services accounts with `kind=AIServices` or `kind=OpenAI`. If they are in a different resource type, contact support.
    - Check that the **Subscription ID** entered in the integration matches the subscription where your agents are deployed.
  </Accordion>

  <Accordion title="Usage statistics show as zero or unavailable (v2)">
    - Verify that **Application Insights is connected** to your AI Foundry project (Foundry Portal → Settings → Tracing).
    - Verify the service principal has **Log Analytics Reader** on the Log Analytics workspace linked to Application Insights (found under App Insights → Settings → Linked workspace).
    - Traces appear within minutes of the first agent invocation. If no invocations have occurred, usage metrics will correctly show zero.
  </Accordion>

  <Accordion title="Usage statistics show as zero or unavailable (v1 Classic)">
    - Classic usage is collected via the Assistants API (Threads and Run Steps) — no Log Analytics configuration is needed.
    - Verify the service principal has data plane access (`Azure AI User` or `Cognitive Services OpenAI User`) on the Azure OpenAI resource.
    - If no threads or runs exist for an assistant, usage will correctly show zero.
  </Accordion>

  <Accordion title="Content filters showing as unavailable for some agents">
    Content filter data is only available for **Azure AI Foundry (v2)** agents. Classic (v1) assistants do not expose this via API — this is an Azure limitation, not a configuration issue.
  </Accordion>

  <Accordion title="403 Forbidden errors during sync">
    - The service principal may not have the role assigned at the correct scope. Verify the role assignment is at **subscription** level, not resource group or resource level only.
    - Role assignments can take a few minutes to propagate after being created.
  </Accordion>

  <Accordion title="Classic assistants not being discovered">
    Classic assistants require the service principal to have data plane access to the Azure OpenAI resource. With `Azure AI User` at subscription level this is covered automatically. With the granular setup, verify that `Cognitive Services OpenAI User` is assigned on the specific OpenAI resource.
  </Accordion>
</AccordionGroup>
