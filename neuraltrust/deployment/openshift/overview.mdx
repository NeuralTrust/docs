The same [`neuraltrust-platform`](https://github.com/NeuralTrust/neuraltrust-platform) chart installs on OpenShift as on any other Kubernetes distribution. Three things differ: the endpoints are served by the OpenShift router as **Routes**, TrustGate's wildcard Routes need cluster-level admission, and the Firewall needs an SCC decision when it runs in your cluster. Everything else — Secrets, values, `ntctl install` or `helm upgrade --install` — is identical.

Every topology is supported. Install by following [Hybrid](/neuraltrust/deployment/hybrid) or [Self-hosted](/neuraltrust/deployment/external) as written — namespace, Secrets, values file, `helm upgrade --install`, verification — and apply the OpenShift specifics on this page as you go.

## Requirements

| Requirement | Detail |
| --- | --- |
| OpenShift | **4.10+** · 4.17+ to attach your own Route certificates via `externalCertificate` |
| Helm | 3.8+ (OCI installs) |
| Access | `oc` access to the target project, cluster-admin for the SCC and IngressController steps |
| Domain | A wildcard apps domain such as `apps.example.com` |
| Datastores | Reachable PostgreSQL and Redis — [minimum sizes](/neuraltrust/deployment/configuration#managed-stores) |

A companion [OpenShift guide](https://github.com/NeuralTrust/neuraltrust-platform/blob/main/README-OPENSHIFT.md) is maintained next to the chart.

## Prepare a project

```bash
oc login https://api.<cluster>:6443
oc new-project neuraltrust
oc get storageclass
```

Create and link the registry pull Secret:

```bash
oc secrets link default gcr-secret --for=pull -n neuraltrust
oc secrets link builder gcr-secret --for=pull -n neuraltrust
```

## Select the platform

[ntctl](/neuraltrust/deployment/ntctl) detects OpenShift from the cluster and
sets the platform for you. Log in with `oc login`, then install as the
[Hybrid](/neuraltrust/deployment/hybrid) or
[Self-hosted](/neuraltrust/deployment/external) page says, passing the cluster's
apps wildcard suffix as the base domain:

```bash
ntctl install --domain apps.example.com                  # Hybrid
ntctl install --mode external --domain apps.example.com  # Self-hosted
```

With Helm, these values switch the chart to OpenShift behaviour:

```yaml
global:
  platform: openshift
  domain: apps.example.com   # usually the cluster's apps wildcard suffix
  ingress:
    provider: openshift
```

For **Hybrid**, the chart's tracked [`values-openshift.yaml`](https://github.com/NeuralTrust/neuraltrust-platform/blob/main/values-openshift.yaml) sets them, together with `global.deploymentMode: hybrid`. It is an overlay, not a complete install: layer it over a values file that selects products, with the OpenShift file last so its settings win:

```bash
helm upgrade --install neuraltrust-platform \
  oci://europe-west1-docker.pkg.dev/neuraltrust-app-prod/helm-charts/neuraltrust-platform \
  --version <VERSION> \
  --namespace neuraltrust \
  -f values-required.yaml \
  -f values-openshift.yaml \
  --set global.domain=apps.example.com
```

For **Self-hosted**, do not use `values-openshift.yaml`, because it switches the install to Hybrid. Put `global.platform: openshift` and `global.domain` in your own values file instead.

Render before you install, declaring the Route API so the OpenShift objects appear:

```bash
helm template neuraltrust-platform <chart> \
  -f values-required.yaml -f values-openshift.yaml \
  --api-versions route.openshift.io/v1
```

## Routes

With `global.platform: openshift`, the console, its API and TrustGuard are
Ingresses with the `openshift-default` class, which the router serves as edge
Routes. TrustGate's gateway and MCP render native Routes; to standardise them on
Kubernetes Ingress instead, set `agentgateway.ingress.resourceType: ingress`.

Dynamic gateway subdomains (`*.llm.<domain>`, `*.mcp.<domain>`) render as Routes with `wildcardPolicy: Subdomain`. The chart cannot configure the IngressController, so a cluster administrator has to admit wildcards first:

```yaml
# IngressController spec.routeAdmission
routeAdmission:
  wildcardPolicy: WildcardsAllowed
```

The router certificate must also cover those wildcard hosts. If you would rather not enable wildcards at all, set `agentgateway.config.autoWildcardHosts: false` and use exact hosts, where callers pass the gateway slug as a header instead.

### Route certificates

By default the endpoints use the router's own certificate. An Ingress without a
`tls.secretName` carries no `tls` block, so the router serves its default
wildcard certificate, which already covers hosts under the apps domain. The
chart does not put its self-signed placeholder certificate on OpenShift
endpoints.

To use your own certificate, set the component's `ingress.tls.secretName`. On
the Routes the chart renders itself, a Route is readable by anyone holding
`route/get`, so the chart never copies private keys into one: it renders
`spec.tls.externalCertificate` pointing at your Secret, which requires
**OpenShift 4.17+** and read access for the router service account. On older
clusters, rely on the router's default wildcard certificate.

## SecurityContextConstraints

Every workload a default install renders runs non-root with all capabilities dropped and is compatible with `restricted-v2` as-is, including the hook Jobs that run before an install or upgrade. With `global.platform: openshift`, the chart drops its fixed `runAsUser`/`fsGroup` from in-cluster PostgreSQL and from those Jobs, so the platform-assigned UID applies. No SCC grant is needed unless the Firewall runs in your cluster. Two workloads need a decision then:

| Workload | Why | Options |
| --- | --- | --- |
| **Firewall** gateway and workers | Default `firewall.securityContext` is `runAsUser: 0`, and the model cache path is `/root/.cache/huggingface` | Grant `anyuid` to the `firewall` ServiceAccount, or override `firewall.securityContext` **and** `firewall.config.hfHome` to a path writable by an arbitrary UID |
| **GPU Firewall** workers | Use `hostIPC` for CUDA MPS plus GPU device resources | Requires a dedicated SCC; only relevant if you opt into GPU workers |

Granting `anyuid` to the one ServiceAccount, rather than relaxing the namespace default, is the narrower change:

```bash
oc adm policy add-scc-to-user anyuid -z firewall -n neuraltrust
```

Keep `restricted-v2` for everything else. If your policy forbids `anyuid` outright, raise it before install, or use the NeuralTrust-hosted Firewall — the default — so no Firewall pod runs in your cluster. See [Firewall](/neuraltrust/deployment/configuration#firewall).

If admission refuses a pod, its workload shows no pods at all, only a `FailedCreate` event. `ntctl doctor` reports it as `NT-DR-016` — see [Pods are never created](/neuraltrust/deployment/troubleshooting#pods-are-never-created).

## Expose the entry points

`ntctl install` lists the Routes with whether a router admitted them, and the hosts the cluster's wildcard DNS already covers, so no DNS records are needed when the base domain is the apps domain. With Helm, check them with:

```bash
oc get route -n neuraltrust
```

For hosts outside the apps domain, follow cluster ingress policy for DNS and certificates. In Hybrid you expose two:

- The LLM/proxy Route, targeting the proxy Service's named `http` port (Service port `80`, TrustGate container port `8081`)
- The MCP Route, targeting the MCP Service's named `http` port (Service port `80`, TrustGate container port `8082`)

Then set both URLs in the console, as in [Hybrid → Expose both entry points](/neuraltrust/deployment/hybrid#expose-both-entry-points).

Self-hosted serves the console at `app.<domain>` and its API at `api.<domain>`, plus `trustguard.<domain>` (the evaluation endpoint) and `trustguard-admin.<domain>` for TrustGuard, `data-plane-api.<domain>` when the data-plane API is deployed, and TrustGate's gateway, MCP and admin hosts when TrustGate is installed. Plan network access and certificates for each host the install renders.

## Also plan for

- Worker capacity for your topology — [Capacity](/neuraltrust/deployment/architecture#capacity) (with the NeuralTrust-hosted Firewall, Hybrid: **2** × 8 vCPU / 16 GiB, External: **3**; with the Firewall in-cluster, Hybrid: **3** × 8 vCPU / 32 GiB, External: **4**; autoscale from there)
- Hybrid only: the [network rules](/neuraltrust/deployment/hybrid#network) for config-sync, telemetry, and DataBridge egress, plus the NeuralTrust inbound source IP
- Disconnected clusters: mirror every image and set `global.imageRegistry` with `global.imageRegistryScope: all` — see [Container images](/neuraltrust/deployment/images). Hybrid cannot be air-gapped, because product telemetry egress is mandatory; a fully disconnected install must use [Self-hosted](/neuraltrust/deployment/external)
