NeuralTrust supports **SaaS**, **Hybrid**, and **External**. SaaS is fully operated by NeuralTrust. Hybrid runs the request-path **data plane** in your environment and keeps the **control plane** on NeuralTrust SaaS. [External](/neuraltrust/deployment/external) runs every plane — control, data, and analytics — in your own cluster with no runtime SaaS dependency. This guide covers Hybrid; see the [External (self-hosted)](/neuraltrust/deployment/external) guide for the fully self-hosted topology.

| Plane | Where it runs | What you care about |
| --- | --- | --- |
| **Control plane** | NeuralTrust SaaS | Console, configuration, analytics |
| **Data plane** | Your environment (Hybrid) | TrustGate, TrustGuard, Firewall (with TrustGuard), DataAgent (one per product) |

## How the planes connect

Hybrid sends configuration requests and metadata outbound while raw prompts and responses stay in **your** PostgreSQL.

```text
 Your environment (data plane)          NeuralTrust SaaS (control plane)
 ┌─────────────────────────┐            ┌────────────────────────────┐
 │ TrustGate  → TrustGuard │ ─────────▶ │  Configuration service     │
 │ (+ Firewall with Guard) │            │                            │
 │        │ OTLP           │            │                            │
 │        ▼                │            │                            │
 │ DataAgent + egress ─────────────────▶│  OTLP metadata / analytics │
 │ collector           ────────────────▶│  Enrolled retrieval        │
 └───────────┬─────────────┘            └────────────────────────────┘
             │
             ▼
    Your PostgreSQL + Redis
```

1. **Traffic path** — Clients hit TrustGate in your environment; TrustGate calls TrustGuard, which calls Firewall, on the request path.
2. **Metadata** — TrustGate and TrustGuard send metadata over OTLP to a collector inside your cluster, which forwards it to SaaS. Payloads are not exported.
3. **Configuration sync** — TrustGate and TrustGuard pull configuration from the SaaS control plane. The data plane initiates this outbound connection; config sync does not require an inbound control-plane connection into your network.
4. **Retrieval** — DataAgent uses the same enrollment token for authorized retrieval over DataBridge.
5. **Gateway traffic** — Clients use separate LLM/proxy and MCP entry points.

Every connection above is initiated from your environment. Nothing dials in.

DataAgent is not optional once you run TrustGate or TrustGuard. Each of those
products needs its own enrolled DataAgent, because the metadata path in step 2
runs through the collector co-located with it. Only a red-teaming-only
deployment — `global.products.dataPlane` alone — runs without one.

Managed PostgreSQL and Redis are recommended for production. The chart can run in-cluster stores for evaluation and non-production use. See [Configuration](/neuraltrust/deployment/configuration#managed-stores) for guidance. For regional resilience, see [High availability](/neuraltrust/deployment/high-availability).

## Choose a deployment method

The private gateway wizard offers three deployment methods:

| Method | Use it for | Wizard output |
| --- | --- | --- |
| **Kubernetes** | **Recommended for production-grade deployments** | Generated credential and setup input to map into the maintained chart or manifests |
| **Docker** | Local development and evaluation of the LLM/proxy path | Generated Docker Compose command |
| **Manual** | Custom or operator-managed deployments | `CONTROL_PLANE_JWT` and `DATA_AGENT_JWT` |

## Create a private TrustGate gateway

<Note>
Each product runs as a separate console object with its own credentials. A Hybrid
install that also runs TrustGuard must create a **private TrustGuard** in
**TrustGuard → Agent Runtime** as well, and collect its own config-sync and
enrollment tokens. See [Console setup](/neuraltrust/deployment/console-setup) for
the full token flow and how to map both products' tokens into chart Secrets.
</Note>

1. Open **TrustGate** and choose **New Gateway**.
2. Enter a gateway name and choose **Private**.
3. Choose **Kubernetes**, **Docker**, or **Manual**.
4. Follow the deployment guidance outside the app:
   - For Kubernetes, use the maintained `neuraltrust-platform` chart or manifests as the deployment source. Review and map the wizard-generated credentials and settings into the current chart interfaces before applying anything.
   - For Docker, the generated Compose path starts the LLM/proxy entry point on `8081`. It does not currently start or expose the MCP process.
   - Manual provides the two JWT values needed by a custom deployment.
5. Expose both TrustGate entry points:
   - **LLM/proxy** — TrustGate port `8081`
   - **MCP** — TrustGate port `8082`
6. Enter the LLM/proxy URL as the wizard's bootstrap **Dataplane URL**, then choose **Save and Finish**. The wizard initially uses this URL for both entry points.
7. Open **Settings → Agent Gateway → General** and set or verify the separate **LLM URL** and **MCP URL**.

For production MCP support, use Kubernetes. For local MCP testing, run the full local TrustGate stack that includes the MCP process. When both entry points run locally, use one hostname with separate ports:

- LLM URL: `http://gateway.example:8081`
- MCP URL: `http://gateway.example:8082`

For Kubernetes, expose two ingress hosts:

- LLM URL: `https://gateway.example.com`
- MCP URL: `https://mcp.example.com`

Both URLs must be reachable by their intended clients. The maintained Kubernetes chart creates separate gateway and MCP Services and Ingress resources.

The wizard-generated Kubernetes `values.yaml` contains credentials directly. Treat the file as a secret, do not commit it, and move credentials into pre-created Kubernetes Secrets or an approved secret manager for production. See [Configuration](/neuraltrust/deployment/configuration) and [Secrets](/neuraltrust/deployment/secrets).

## Manage the gateway

Open **Settings → Agent Gateway**:

- **General** lets you edit the Hybrid gateway's **LLM URL** and **MCP URL** independently.
- **Deployment** can regenerate private install configuration and credentials.

Consumer connection snippets use the two configured URLs separately.

## Network requirements

Allow outbound connections from the Hybrid data plane to NeuralTrust for
configuration pulls, metadata export, and DataAgent enrollment or retrieval.
TrustGate and TrustGuard initiate config-sync; DataAgent reaches DataBridge.
Config-sync and DataBridge are **outbound-only** — you do not open inbound
ports for those services.

For the exact hostnames, IPs, and the NeuralTrust inbound source IP to allow
at your edge, see [Hybrid network allowlist](/neuraltrust/deployment/network).

Also allow the data plane to reach your LLM providers, PostgreSQL, Redis, and
container registry. Allow clients to reach the configured LLM and MCP URLs.

The Helm chart is developed in the open at
[NeuralTrust/neuraltrust-platform](https://github.com/NeuralTrust/neuraltrust-platform).
These pages are the task-oriented guide; the repository is the reference, and it
is worth a look if you are the person actually running the platform.

| There | What it gives you |
| --- | --- |
| [`values.yaml`](https://github.com/NeuralTrust/neuraltrust-platform/blob/main/values.yaml) | Every setting the chart accepts, with its default |
| [`SECRETS.md`](https://github.com/NeuralTrust/neuraltrust-platform/blob/main/SECRETS.md) | Exhaustive per-component Secret and key contract |
| [`VALUES_SCENARIOS.md`](https://github.com/NeuralTrust/neuraltrust-platform/blob/main/VALUES_SCENARIOS.md) | Worked scenarios and the values that implement them |
| [`docs/`](https://github.com/NeuralTrust/neuraltrust-platform/tree/main/docs) | Architecture contract, sizing, network, observability |
| [`values-*.yaml.example`](https://github.com/NeuralTrust/neuraltrust-platform) | Starting points for each topology |
| [CHANGELOG](https://github.com/NeuralTrust/neuraltrust-platform/blob/main/CHANGELOG.md) · [Issues](https://github.com/NeuralTrust/neuraltrust-platform/issues) | What changed between versions, and where to report problems |

All of it also ships inside the chart artifact, so `helm pull <chart-ref>
--version <VERSION> --untar` gives you the copy that matches the version you run
— see [Get the chart sources](/neuraltrust/deployment/quickstart#get-the-chart-sources).
