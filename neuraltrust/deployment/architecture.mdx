This is the page to hand to a platform or infrastructure team before an install.
It covers what the platform depends on, what talks to what, and how much capacity
to plan for — independent of which model you deploy.

For the topology itself, including its diagram and component inventory, go to your
model's guide: [Hybrid](/neuraltrust/deployment/hybrid),
[External](/neuraltrust/deployment/external), or
[Central](/neuraltrust/deployment/central). Everything ships as a **single
umbrella Helm chart**,
[`neuraltrust-platform`](https://github.com/NeuralTrust/neuraltrust-platform),
with one value selecting the topology:

```yaml
global:
  deploymentMode: hybrid # hybrid | external | saas
```

## Infrastructure dependencies

The chart can run every datastore in-cluster for evaluation. **Recommended for
production** is managed PostgreSQL and Redis (`deploy: false` plus a host you
provide) with ClickHouse left in-cluster. The in-cluster default exists so a
proof of concept can `helm install` without provisioning those services first.

| Dependency | Required | Chart can deploy it | Version the chart ships | Port | Used for |
| --- | --- | --- | --- | --- | --- |
| **PostgreSQL** | Yes | Yes (`global.postgresql.deploy`) | 17 | 5432 | Product data, raw payloads, control-plane state |
| **Redis** | Yes | Yes (`global.redis.deploy`) | 7.2 | 6379 | Rate limiting, evaluation progress |
| **ClickHouse** | External and Central only | Yes (`infrastructure.clickhouse.deploy`) | 26.7 | 8123 / 9000 | Self-hosted analytics and telemetry |
| **Ingress or Routes** | Yes | Renders the objects | — | 443 | Public entry points |
| **StorageClass** | Yes, when running in-cluster stores | No | — | — | PostgreSQL, Redis, ClickHouse volumes |
| **Container registry** | Yes | No | — | 443 | Image pull, or your mirror |
| **LLM providers** | Yes, for the gateway path | No | — | 443 | Upstream model calls |
| cert-manager | No | No | — | — | TLS automation, if you use it |
| External Secrets Operator | No | No | — | — | Credential delivery, if you use it |
| Object storage (S3 / Azure Blob) | No | No | — | 443 | ClickHouse backups |
| SMTP or email provider | External and Central only | No | — | 587 / 443 | Console invitations |

Redis is **not** optional and it is not only a cache: TrustGate uses it for rate-limit
and budget counters on the request path. Redis OSS is sufficient —
there is no Enterprise-only feature in use. The chart's in-cluster Redis runs a
plain `redis-server`.

## Ports between components

In-cluster hops are plain Services; there is no service mesh requirement.

| Component | Port | Reached by |
| --- | --- | --- |
| TrustGate proxy | 8081 | Your clients, through Ingress |
| TrustGate MCP | 8082 | Your MCP clients, through Ingress |
| TrustGate admin | 8080 | Console (External and Central only) |
| TrustGuard data plane | 8081 | TrustGate |
| Firewall gateway | 8000 | TrustGuard |
| data-plane API | 8000 | Console and TrustTest |
| DataAgent | 8080 | Health probes only — it has no inbound service |
| ClickStack collector | 4317 / 4318 | TrustGate, TrustGuard (OTLP) |
| ClickHouse | 8123 / 9000 | Collector, DataCore, AlertEngine, data-plane API |
| DataBridge northbound | 50051 | DataCore, in-cluster (Central only) |
| DataBridge southbound | 443 | Remote DataAgents (Central only) |

What has to cross a network boundary depends on the model, and each model page
carries its own rules: [Hybrid](/neuraltrust/deployment/hybrid#network) needs
outbound HTTPS to NeuralTrust plus one inbound source IP,
[External](/neuraltrust/deployment/external#network) needs neither, and
[Central](/neuraltrust/deployment/central#network-rules) needs the same outbound
set as Hybrid but against your own domain, with the central cluster accepting it.

## Capacity

Kubernetes schedules a pod only onto a node with enough unreserved capacity to
cover the pod's resource **requests**. Cluster size is therefore set by the
chart's default requests rather than by traffic: the node counts below are the
smallest pools on which every component of a new installation can be scheduled.
Treat them as the minimum of an autoscaling node pool, and let the cluster add
nodes as load grows.

| Scenario | Firewall on CPU | Firewall on GPU |
| --- | --- | --- |
| Hybrid, all products | **3** × 8 vCPU / 32 GiB | **2** × 8 vCPU / 16 GiB + **2** × L4 GPU nodes |
| Hybrid, TrustGuard only | **3** × 8 vCPU / 16 GiB | **2** × 8 vCPU / 16 GiB + **2** × L4 GPU nodes |
| Hybrid, TrustGate only | **2** × 8 vCPU / 16 GiB | — (no Firewall) |
| External or Central | **4** × 8 vCPU / 32 GiB | **3** × 8 vCPU / 16 GiB + **2** × L4 GPU nodes |

| Node | AWS | Azure | GCP |
| --- | --- | --- | --- |
| 8 vCPU / 32 GiB | `m6i.2xlarge` | `Standard_D8s_v5` | `e2-standard-8` |
| 8 vCPU / 16 GiB | `c6i.2xlarge` | `Standard_F8s_v2` | `c4-highcpu-8` |
| L4 GPU node: 8 vCPU / 32 GiB, one NVIDIA L4 | `g6.2xlarge` | No L4 size; not validated | `g2-standard-8` |

Each count allows for the cluster's own components — the node's system
reservation, DaemonSets, and kube-system — and keeps total requests at or below
85 % of allocatable capacity. The remaining 15 % absorbs the extra pod a rolling
upgrade creates. With one node fewer, the installation cannot be scheduled.
Where a single node would be enough, the table specifies two, so that the two
replicas of the request path run on different nodes.

The GPU column assumes the
[GPU Firewall configuration](/neuraltrust/deployment/configuration#gpu-firewall-workers),
including CUDA MPS sharing with four clients per GPU.

<Tip>
**Enable cluster autoscaling.** Set each node pool's minimum to the count above
and its maximum at least two nodes higher. Capacity for additional replicas,
upgrades, and node failures is then added when it is needed, rather than
provisioned in advance.
</Tip>

### What the chart requests

These totals sum the requests of every replica and sidecar in the default
render, with the request path at two replicas and PostgreSQL and Redis running in
the cluster. Values are rounded up to whole vCPU and GiB.

| Scenario | Firewall on CPU | Firewall on GPU: CPU pool | Firewall on GPU: GPU pool |
| --- | --- | --- | --- |
| Hybrid, all products | 13 vCPU / 37 GiB | 6 vCPU / 15 GiB | 7 vCPU / 28 GiB, 7 GPU shares |
| Hybrid, TrustGuard only | 9 vCPU / 25 GiB | 3 vCPU / 6 GiB | 6 vCPU / 24 GiB, 6 GPU shares |
| Hybrid, TrustGate only | 3 vCPU / 6 GiB | — | — |
| External | 18 vCPU / 46 GiB | 11 vCPU / 24 GiB | 7 vCPU / 28 GiB, 7 GPU shares |
| Central | 19 vCPU / 47 GiB | 12 vCPU / 25 GiB | 7 vCPU / 28 GiB, 7 GPU shares |

Using managed PostgreSQL and Redis lowers memory requests by 2 GiB. The totals
exclude the node's system reservation, DaemonSets, kube-system, and your ingress
controller or Gateway; the node counts above already allow for them.

Requests describe what the scheduler reserves, not the throughput an
installation sustains. Measure under your own traffic before tuning.

| What drives capacity | Default request / limit | Notes |
| --- | --- | --- |
| Firewall CPU workers | 1 vCPU / 3 GiB each, limit 2 vCPU / 4 GiB | Seven with all products. `prompt-moderation` requests 4 GiB (limit 6 GiB) and `topic-guard` is limited at 5 GiB. Together they are 60 % of Hybrid's memory requests |
| data-plane API | 1 vCPU / 3 GiB per replica, two replicas | Runs evaluations in-process by default |
| ClickHouse | 1 vCPU / 4 GiB, limit 4 vCPU / 8 GiB | External and Central; keep headroom for analytics queries |
| PostgreSQL and Redis | 500m / 2 GiB and 100m / 128 MiB in-cluster | Prefer [managed stores](/neuraltrust/deployment/configuration#managed-stores), so datastore capacity is independent of the node pool |

To adapt capacity to your workload, scale out the gateway and TrustGuard
replicas that carry the most traffic, or enable horizontal pod autoscaling once
the cluster exposes metrics. Run only the Firewall detectors you use, and pin
workloads to a dedicated node pool when they must be isolated from other tenants
of the cluster.

### Datastore sizing floors

| Store | Minimum for production | Notes |
| --- | --- | --- |
| PostgreSQL | 2 vCPU, 4 GiB RAM, 20 GiB storage | Grows with retained raw payloads |
| Redis | 1 GiB memory | No persistence requirement |
| ClickHouse | 50 GiB volume, 4 GiB memory | External and Central; scale with retention |

## Not required

Deployments sometimes budget for these because older material mentioned them, or
because comparable products need them. Platform v2 does **not**:

| Not required | Why |
| --- | --- |
| **Kafka** or any message broker | Removed in v2. Telemetry is OTLP; the legacy Kafka pipeline ended with chart v1. |
| **AISPM** | Retired. AlertEngine covers SIEM forwarding. |
| **Agent Guardians** | Not in the v2 platform chart. |
| **Control-plane Scheduler** | Removed in v2 (`CONTROL_PLANE_SCHEDULER_URL` is dead). |
| **data-plane Kafka workers** | Removed with the Kafka pipeline. |
| A dedicated **vector database** | There is no Milvus, Qdrant, or pgvector requirement. |
| A **service mesh** | In-cluster hops are plain Services. |
| **GPU nodes** | CPU Firewall images are the default; GPU is opt-in for higher throughput. |

If you are working from documentation or a diagram that shows Kafka, AISPM,
Agent Guardians, or a control-plane Scheduler, it describes the retired v1
platform, not this one.
